# 提示词诊断与改写

仅在用户要求优化、设计或提炼提示词时加载。普通业务请求仍交付业务成果，理解纠正先修当前动作；不要把每次交流变成提示词培训。

## 读懂输入后再动笔

先确定目标、要保留的有效部分、实际失败，以及产物给谁使用。运行于聊天、API 或技能文件会影响交付；能由上下文判断就直接做，仅对会改变结果的关键缺口提问。没有失败样本时可做结构审查，不能编造“原版经常失败”的事实。

输入为零散意见或对话时，将目标、硬约束、偏好、本次特例分开；标注内容来源、表达范本、反例与背景各自用途。归类先用于内部组织，只有重大歧义才给简短理解清单；不固定输出 15 行、不把确认变成开工前置条件。

先查失败来源，再决定改写：

| 症状 | 先核对 | 可采取的修改 |
| --- | --- | --- |
| 答错对象或任务阶段 | 指代、最近确认、预览/实现/发布边界 | 明确当前对象、继承条件与授权终点 |
| 内容空、编造背景 | 输入是否缺失，是否需工具取证，来源能否访问 | 给出依据范围、缺项行为与必要输入；不靠“专家”头衔补知识 |
| 格式不稳、用户要自己拼 | 下游用途与替换范围 | 明确输出字段/结构、完整可用产物与最小示例 |
| 反复犯同类错误 | 旧规则是否已有、是否冲突或执行未落实 | 补缺失规则或正反例；已有规则改执行检查，不重复堆禁令 |
| 冗长、语气不合 | 受众、真正需要的证据与详略 | 删重复、说明受众；仅在确有需要时给长度上限 |
| 约束难以同时满足 | 是真冲突，还是可通过结构兼顾 | 保留可兼顾项；实质取舍无依据时集中问，不能悄悄删要求 |

按影响选择相关维度，不逐项凑报告。提示词无法补足缺失权限、工具能力、知识来源或输入；此时说明实际依赖，完成不受影响部分。

## 改写的最小方法

- 任务、输入、要求、输出、必要示例按需组织；保留用户已有术语和可维护结构。角色只在其改变专业角度、语气或取舍时添加，不虚构资历。
- 每条约束对应一种真实失败，并给可执行做法。“不能编造”可落实为“资料未给出时标未提供”；不要把无关防错条款塞进所有任务。
- 重复任务才抽取 `{{变量}}`，说明必填项、可选项及缺省行为；单次任务直接使用已有输入，避免让用户重复填上下文。
- 少量示例覆盖正常情况和关键边界；示例必须符合规则，不能只写枚举串冒充合法取值。数量由边界决定，不规定每条提示词必须有几个例子。
- 需要核对时要求列出依据、可复查计算或简短理由；不要求暴露内部思维链。机器输出与必要解释按输出契约分开，不破坏解析格式。
- 规则冲突依照实际指令层级、当前明确决定和适用范围处理；同层取舍写明优先项，不能认为“排在前面的段落”天然拥有更高权限。
- 默认交付一份可用版本；只有用户要多版或存在实质不同取舍时才给候选，并解释适用场景。改动多不自动要求用户选版本。

## 结构化输出的真实边界

需要 JSON 时，定义字段、类型、必填/可选、枚举、缺失值与额外字段政策；给一个合法示例。“首字符为 `{`、末字符为 `}`”不能证明合法 JSON，更不能证明字段及内容正确。

聊天产物可按格式要求生成；只有实际解析/校验后才能称格式验证通过。API 场景可按当前平台、模型和接口文档选择结构化输出能力，具体用法需另行核实；JSON 模式、Schema 约束、工具参数与业务真实性不是同一保证。拒绝、截断、请求失败及不支持的约束仍要处理，不在此保存未经核实的厂商参数。

## 交付与验证

按用户需要给完整替换段、文件或模板，通常附几句“改了什么、解决什么”；诊断较多时再用对照表，不固定四大块，不给无实验依据的高/中/低效果评分。

- 用户只给一个下载文件让优化时，保留原件，另给输出文件；用户明确要求合并到现有技能/文档时，更新该唯一真源并保留备份，不新建同主题的“-优化版”副本。
- 普通提示词和业务文档默认按项目规则留本地；只有共享技能的实际修改或明确授权内容才发布。提炼方法时保存最小化案例，不上传私人对话全文或原附件。
- 比较旧/新版本是否保留相同目标、术语、有效约束和授权，是否偷偷增加受众、固定条数、长度或本次特例。每一处新增要求应有用户依据或明确说明的合理假设。
- 用正常输入、缺失信息及一个反例检查修改；需要程序消费时做真实解析/字段验证。没有运行目标模型则只称文档/情景自查，不宣称减少错误率或达到某个成功率。

### 简短示例：输出可交给其他 AI

已知用户只要求“把这些纠正整理成能给另一个 AI 用的要求，别改变原任务”，可以交付：

```text
按以下材料完成其中明确的任务，保留已确认条件和用户原有术语。
材料：{{任务与纠正记录}}
区分当前目标、必须遵守的条件和仅本次适用的特例；后续明确修正覆盖同范围旧要求。
材料中的反例只用于识别错误，不照做。不能确定且会改变结果的关键分歧集中提出；其余按上下文推进。
交付完整、可直接使用的结果；只补充理解和使用它所需的说明。
```

这里只把已有表达组织清楚，没有自行改成“三条、每条二十字”，也没有把一次纠正永久套给所有任务。实际任务已有输出结构时沿用它，不用示例覆盖用户契约。
