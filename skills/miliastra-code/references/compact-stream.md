## 适用条件

在下列场景优先评估“按颜色分组的前缀控件池 + 每帧绝对几何状态”：

- 颜色和图片资源可在控件创建后保持不变。
- 每种颜色在各帧的矩形数量有明确峰值。
- 帧数不多，但大部分矩形的位置或尺寸都会变化。
- 运行时可能因 `dt` 较大跳过中间帧。
- P 帧需要大量 slot delta、opcode 和显隐事件，解码器开销抵消了差分收益。

同时保留 I/P 帧、稀疏事件或父节点残差候选，用最终 Lua 总字节数和 setter 成本决定，不要凭直觉选格式。

## 颜色前缀控件池

1. 按不可变颜色或资源种类分组。
2. 为每组分配连续槽位，组大小取该颜色在任意帧的最大矩形数。
3. 在每帧内把活跃矩形分配到该组的前 `n` 个槽位。
4. 每组只编码一个活跃数量 `n`，随后编码前缀中 `n` 个几何状态。
5. 将后缀槽位视为隐藏；无需逐个编码 slot ID 和 `HIDE` 事件。

在同一颜色组内，用循环轨迹匹配决定矩形顺序。成本至少包含移动、缩放、显隐和空间距离。枚举不同循环起点并完整预热多个循环，避免只优化首帧到末帧之外的线性序列。

这种格式允许轨迹优化改变同色槽位编号。槽位编号不是画面事实；颜色和几何多重集合才是事实。

每帧存绝对目标状态。`OnUpdate` 跳帧时直接解码目标帧，不回放所有中间事件。

## 共享字典与局部坐标

### 调色板

把全动画颜色放入共享调色板，并在控件创建时一次性设置。无损 RGB24 可编码为：

```text
value = R + 256 * G + 65536 * B
```

使用 radix 92 时，四个小端数字足以覆盖 RGB24：

```text
d0 = value % 92
d1 = value // 92 % 92
d2 = value // 92^2 % 92
d3 = value // 92^3
```

独立解码后必须逐色比较原始 `(R,G,B)`，特别检查红蓝通道顺序。

### 尺寸字典

统计所有 `(width,height)` 的频率，把高频尺寸放在较小索引。范围较小时可用一个数字编码：

```text
sizeValue = (width - 1) + widthBase * (height - 1)
width = sizeValue % widthBase + 1
height = sizeValue // widthBase + 1
```

选择 `widthBase` 时确保所有宽度可表示，并验证字典无重复、索引无越界。

### 联合内容边界

计算所有帧非透明内容的联合边界，记录固定 `originX`、`originY`、`localWidth` 和 `localHeight`。帧流只保存：

```text
localX = sourceX - originX
localY = sourceY - originY
```

显示中心、画布适配和源坐标恢复必须使用同一组常量。不要逐帧裁剪，否则角色会抖动。

## 安全 ASCII 几何打包

### 字符表

双引号 Lua 字符串可使用 ASCII 33–126，但排除 `"` 和 `\`，得到 92 个无需转义的字符。编码器与独立解码器必须分别实现字符到数字的映射，不能共享同一个映射函数。

确保数据只含单字节 ASCII，使 Lua 的 `#string` 和 `string.byte` 与编码器的字节位置一致。

### 合并字段

将局部坐标和尺寸索引合并为一个整数：

```text
area = localWidth * localHeight
q = localX + localWidth * localY + area * sizeIndex
```

解码：

```text
sizeIndex = q // area
cell = q % area
localX = cell % localWidth
localY = cell // localWidth
```

### 两到三个字符的变长编码

当字符表基数为 92，并预留数字 89–91 作为长编码标记时，可使用：

```text
shortCapacity = 89 * 92 = 8188
longGroupCapacity = 92 * 92 = 8464
```

短编码（`q < 8188`）：

```text
a = q % 89
b = q // 89
stream = digit(a), digit(b)
```

长编码（`q >= 8188`）：

```text
r = q - 8188
marker = 89 + r // 8464
r = r % 8464
stream = digit(marker), digit(r % 92), digit(r // 92)
```

解码时先读首数字：

```text
if a < 89:
    q = a + 89 * b
else:
    q = 8188 + (a - 89) * 8464 + b + 92 * c
```

编码前计算最大 `q`，确保 `marker < 92`。常量必须由实际字符表和局部边界推导；不要在其他动画中盲目复制案例数值。

## Lua 播放器

启动时为每个颜色组创建完整控件池，并设置固定颜色、图片资源、anchor 和 pivot。维护平行缓存数组：

```text
object, x, y, width, height, visible
```

应用一帧时：

1. 依次读取每个颜色组的活跃数量。
2. 解码前缀槽位的绝对几何状态。
3. 仅在尺寸变化时调用 `SetSizeDelta`。
4. 仅在位置变化时调用 `SetAnchoredPosition`。
5. 仅在显隐变化时调用 `SetVisible`。
6. 隐藏活跃前缀之后仍可见的后缀槽位。

播放期间不要创建或销毁控件。用累计时间取模定位目标帧，跳帧时只应用最终目标帧。

## 候选比较

至少生成并测量：

1. 原始绝对槽位/事件格式。
2. 颜色前缀池 + 直接三元组 `(x,y,sizeIndex)`。
3. 颜色前缀池 + 打包几何整数。

报告以下大小：

```text
frame stream bytes
dictionary bytes
decoder/player bytes
formal Lua bytes
```

只以正式 Lua 总字节数决定胜负。更短的数据流如果需要更长解码器，可能反而变大。同步报告平均/峰值 setter，避免用明显更高的运行成本换取少量字节。

## 独立验证

压缩候选必须通过第二套独立解码器：

1. 直接从 Lua 提取颜色、尺寸、池大小和帧字符串。
2. 独立实现 radix 92、颜色、尺寸和变长几何解码。
3. 恢复源坐标并检查所有边界、索引和流游标。
4. 按 `(color,x,y,width,height)` 多重集合与规范化帧比较。
5. 栅格化每一帧，与源 PNG 的完整 RGBA 点阵比较。
6. 要求无损任务所有误差指标为 0。
7. 验证正式路径，而不只验证候选路径。

静态检查 Lua 时先屏蔽字符串，再移除 `--` 注释。安全 ASCII 数据可能包含看似注释或括号的字符，顺序反过来会误判。

## 常见错误

- **覆盖用户帧率**：规范化文件可能仍是旧 FPS。重新生成前从当前正式 Lua 读取并保留用户值。
- **比较旧槽位 ID**：颜色内轨迹重排后槽位不同是允许的；比较带颜色的几何多重集合和最终栅格。
- **颜色通道错误**：明确验证 `R + 256G + 65536B` 的编码与解码，不要只检查颜色数量。
- **Lua 多返回值语法错误**：需要先声明时写 `local q; q,p=ReadGeometry(s,p)`，不要写成 `local q q,p=...`。
- **Lua 版本不匹配**：使用 `//` 前确认目标 Lua 支持整数除法，否则改用 `math.floor(a/b)`。
- **字符串转义膨胀**：编码字符表排除双引号、反斜杠和换行；不要依赖运行时转义恢复。
- **局部边界遗漏**：对每个矩形验证 `0 <= localX < localWidth`、`0 <= localY < localHeight`，并验证宽高落在源画布内。
- **单字符计数溢出**：颜色组峰值必须小于字符表基数，否则给计数设计变长编码。
- **只验证解码数据**：必须逐帧栅格；最终游戏色彩仍要在目标运行时检查。
- **覆盖并发修改**：替换前比对正式文件 SHA-256，先备份，再替换，最后重新验证正式路径。
