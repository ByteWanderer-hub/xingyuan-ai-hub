# 新项目架构评估流程（开工前把"架子"定下来）

> **为什么需要这一步**：千星里**改结构最贵** ✗ —— 脚本数、容器层级、变量清单都是**编辑器侧手工**做的 ✓（AI 不能建控件 ✗）。
> 开工前把这几件事定下来，后面就只是"填空" ✓；定错了就得**回编辑器返工** ✗（而且中途改结构容易把已跑通的部分弄坏 ✗）。
> 本流程的输出 = **一张"架子表"** ✓（照着它建编辑器 + 写脚本 ✓）。
>
> **输入**：`miliastra-bb` 的 `需求边界清单_*.md`（含 ```yaml handoff 块：类别 / 确认方案 / 验收口径 / On-Off scope / 撤销条件）✓ ——
> **边界没确认就先回 `miliastra-bb`** ✗ 别在这一步自己替需求拍边界 ✗（这一节定的是"怎么搭"，不是"要什么"）。

**用《侦探杀》（11 脚本 / 40 字段 / 真机跑通 ✓）当参照实例** —— 下文每步都给"判据"和"实例"两栏 ✓。

## Step 0 · 需求切片（先弄清"要做什么规模的东西"）

| 要问清 | 为什么要 |
|---|---|
| **单机还是联机**？几人？ | 联机要区分"本机玩家 / 其他玩家"，状态通道与变量实体都会变 ✓ |
| **一局有多长**？几阶段？ | 决定"状态机"复杂度 ⇒ 决定主控脚本要不要拆 ✓ |
| **有几块"界面"**（主画面 / 弹窗 / 图鉴页 / 结算页…）？ | 直接决定容器与脚本数量 ✓ |
| **有没有"每帧都在变"的东西**（动画 / 粒子 / 计时）？ | 每帧更新必须**独立成脚本** ✓（否则会拖累其它逻辑 ✓ 也更容易被 pcall 冻结 ✗） |
| **谁在什么时候读状态**？（几个读方 ✓） | 决定要不要"推"（`Invoke` / 信号）✓ 还是"拉"（读变量 ✓） |

## Step 1 · 脚本切分（要几个 `.lua`）

**判据（三条，按优先级）**：
1. **单一职责**：一块界面 / 一类逻辑 = 一个脚本 ✓（改 A 不碰 B ✓）
2. **更新频率分层**：每帧更新的（输入 / 动画 / HUD ✓）与"事件驱动"的（弹窗 / 图鉴 ✓）**分开** ✓
3. **数据方向**：**谁写、谁读**要能画成一张单向图 ✓；出现"互相写"就说明切错了 ✗

**实例（《侦探杀》11 个客户端脚本 ✓ 全部挂在同一个容器节点上 ✓）**：

| 脚本 | 一句话职责 | 频率 |
|---|---|---|
| `主控 main` | **唯一状态持有者**：规则、判定、阶段机、写状态 ✓ | 每帧 |
| `交互 input` | 点击/按键热区 → 发指令 ✓ | 每帧 |
| `调查板 board` | 主画面（格子/名单/提示条）+ 自己那块的重画 ✓ | 每帧 |
| `HUD hud` | 左上角/底部常驻信息（时间/名声/滚动日志 ✓） | 每帧 |
| `表现 view` | 覆盖层（术语页 / 详情 / 结算 …）✓ | 每帧 |
| `翻牌 reveal` / `效果引擎 fx` | 翻牌动画 / 粒子特效 ✓ | 每帧 |
| `弹窗 popup` / `图鉴 codex` / `开始场景 start` / `背景层 bg` | 低频：按需出现 ✓ | 事件驱动 |

> ⭐ **经验值**：小玩法 **3~5 个**（主控 + 输入 + 主画面 + 常驻 HUD ✓）；中等玩法 **6~10 个**；
> 每个脚本**别塞两类界面** ✗ —— 后期"改一个地方弄坏另一块"基本都源于此 ✓。
> ⭐ **所有客户端脚本可以挂在同一个容器节点上** ✓（《侦探杀》就是 ✓）—— 它们通过
> `script.object:GetScript(mappingId)` 互相找到 ✓（**不需要**每个脚本一个容器 ✓）。

**记录方式**：把 `mappingId` 记成一张表 ✓（**从 `.gil` 的 `mappings[]` 读 ✓ 别手抄** ✗）。

## Step 2 · 容器与控件树（容器节点下挂哪些容器）

**判据（按"什么时候一起显隐/重建"分组）**：
1. **常驻层**（一直在 ✓）：主画面 / HUD ✓
2. **覆盖层**（按需出现 ✓）：术语/详情/图鉴/结算/弹窗 ✓ —— **各自一个容器** ✓
3. **特效层**（粒子/动画 ✓）：单独容器 ✓（避免动效影响主画面重画 ✓）
4. **背景层**：最底 ✓

**实例（《侦探杀》的容器分组 ✓）**：
```
客户端控件容器（容器节点 = 脚本挂载点 ✓）
├─ 背景层      （最底 ✓ 静态）
├─ 主画面      （格子 16 个 + 名单栏 + 提示条 ✓ 常驻）
├─ 覆盖层      （18 个标题级覆盖层 ✓ 按需显隐）
├─ 特效层      （粒子池 ✓ 第 30 帧晚建 ✓）
└─ HUD         （时间/名声/日志 ✓ 常驻）
```

⚠️ **两个硬约束（AI 不能替你做 ✗）**：
- **想被 `game.InstantiateClientUIControl` 动态创建的控件，必须在"客户端控件模板"库里"存为模板"** ✓
  只在画布上摆实例 ⇒ 创建时**恒返回 nil** ✗（真机实测 ✓）
- **模板必须是"无父节点"的独立控件** ✓（画布上的实例、模板的子节点 ⇒ 一律 nil ✗）
  ⇒ 判断"哪些能动态创建"用 `miliastra_map op=clientui` ✓（它只看无父节点的独立模板 ✓）

## Step 2.5 · 两条"会让界面消失"的硬约束（架构阶段就得写进表里）

> 来源：联动测试 —— 四个运行里**没有**把这两条写进架构表 ✗ ⇒ 说明它们被当成"调样式时的细节"了 ✗。
> 它们其实是**接口契约级**信息 ✓：决定"**谁能被创造**"和"**哪块字根本不会显示**" ✓。

| # | 硬约束 | 症状（都**不报错** ✗） | 架构阶段要写什么 |
|---|---|---|---|
| 1 | **要动态创建的控件，必须先在"客户端控件模板"库里「存为模板」，且模板必须是"无父节点"的独立控件** | `InstantiateClientUIControl` 返回 **nil** ⇒ 静默什么都不建 ✗（画布上摆的实例、模板的子节点，**一律 nil** ✗） | 容器树里**逐条标**：哪些是**模板**（可动态创建 ✓）、哪些只是**画布实例**（只能用 `GetChild` 找 ✓） |
| 2 | **文本框矩形高 ≥ 字号 × 1.4**（CJK 行高；真机实测） | 容不下 ⇒ 该控件**整条不画** ✗（不裁切、不缩小、不报错 ✓ `visible` 仍是 true ✗ **模拟器不模拟** ✗） | 版面表里**每一行都写 `h`** 并按字号自查：`22→≥32 / 28→≥40 / 52→≥80 / 64→≥96` ✓ |

⇒ 于是架构表里**每一行可见区域**必须落到三件事之一：**模板 ✓ / 画布实例 ✓ / 字号对应的 `h`** ✓
（三项缺一，落地时就可能出现"建了但看不见" ✗ —— 而这类问题**排查成本极高** ✓，因为日志全绿 ✓）

## Step 2.6 · 两条"决定可做性"的平台事实（批量测试里 ≥3 个运行各自独立发现 ✓）

**① 平台没有物理引擎** ✗ —— 这条**不是工程细节，是硬边界** ✓

- 实测：客户端 UI API 全表（153 条）里检索 `physics|物理|Raycast|刚体|重力` ⇒ **只命中 `raycastTarget`**（那是光标射线 ✗）⇒ **没有碰撞/重力/刚体** ✓
- ⇒ 任何"切开 / 坍塌 / 堆叠 / 抛物 / 绳索物理"的玩法，**都要手写几何**（AABB 求交 + 自算积分）✓
- ⇒ 立项时就要把它写成一句结论：**"这不是复刻玩法，是复刻玩法 + 半个物理引擎"** ✓
  （有真机先例：《双相》手写 AABB 平台物理、《侦探杀》手写栅格几何 ✓ ⇒ **可做** ✓ 但要排工期 ✓）
- ⇒ 玩法依赖"真实刚体坍塌"（如拆楼类）时 ⇒ 按 **`miliastra-bb` 的 ⛔「官方不支持」流程**处理：
  给 2~3 条**替代路线** ✓ 并说清"哪条会让某条需求原文名存实亡、必须重写 R 并重过映射" ✓

**② 文档内部有一处冲突，按"真机为准"处理** ⚠️

| 来源 | 说法 |
|---|---|
| `api-client-ui.md`（约 658 行） | 列了 `SetLocalRotation(x, y, z)` ✓ |
| `engine-boundaries.md` 第 25/26 条（**真机实测**） | **`rotationZ` 写不进去**（返回 false）✗ |

- ⇒ **方案里不要依赖"旋转某条控件"** ✗：要用斜线就用 **8px 分段拼** ✓；素材朝向问题**只能请创作者在编辑器里转** ✓
- ⇒ 顺带一条规律：**凡是"文档说有、真机没验"的接口，先按"可能不生效"设计** ✓ 并留探针 ✓
  （这条与 `miliastra-code` §2 的"证据双轴"一致 ✓ —— `documented` ≠ `observed` ✓）

## Step 2.7 · 一条来自"每帧几何"的架构律（批量测试里由平台跳跃类玩法收敛出的 ✓）

**"物理积分"与"世界渲染"必须在同一个脚本里** ✓ —— 三条理由，缺一不可：

| # | 理由 | 后果 |
|---|---|---|
| 1 | **几何每帧都在变** | 走"变量 + 信号" = **异步晚一拍** ✗ ⇒ 动作/手感类玩法直接崩 ✗ |
| 2 | **跨脚本层级不可控**（谁后建看脚本执行顺序 ✗） | 世界对象**彼此全在互压** ✓ ⇒ 拆到两个脚本必然打架 ✗ |
| 3 | ⭐ **`script:Invoke` 没有返回值** | 渲染方**无法"拉"几何** ✗ ⇒ 只能由"算的那一方"**推** ✓ —— 那它就该自己画 ✓ |

⇒ **正解**：**世界层 = 单脚本 + 单容器** ✓，层级由**脚本内的创建顺序**决定 ✓；
   确实要分层时，可按已运行对话工程使用命名容器与独立挂载脚本；逐节点约定职责与层序。范例确认不替代新工程视觉验收，见 [对话工程参考](dialog-template-patterns.md)。
⇒ **反例（别这么分）** ✗：`physics.lua` 算位置 + `render.lua` 画画面 —— 在千星里会退化成"**每帧推一堆 `Invoke`**"，
   既晚一拍、又凭空多出一堆契约错位点 ✗。
⇒ **推广**：凡是"**每帧都变的量**"（位置 / 长度 / 朝向 / 血量条 / 锚点），
   一律**由持有它的那个脚本自己画** ✓ —— 别跨脚本传 ✗（这条与 `ui-data-ownership.md` 的时机差是同一条道理 ✓）。

## Step 3 · 自定义变量清单（挂哪个实体 / 挂哪些）

客户端 `PlayerSelf` 可读：已有《侦探杀》记录，且 2026-10-18 用户确认运行的对话/任务工程多处实际使用；`AvatarSelf` 在通用解析器中有支持分支，具体角色变量读值仍需实例证据。按数据归属选 Level / PlayerSelf / AvatarSelf，不能把“只验过 Level”当限制。详见 [对话工程参考](dialog-template-patterns.md)。

| 实体 | 用途与证据边界 |
|---|---|
| Level | 关卡共享状态，按当前关卡契约读取 |
| PlayerSelf | 本机玩家配置、任务、身份；范例读 guid、任务字典并监听变化 |
| AvatarSelf | 当前角色数据；文档与解析器支持，具体字段另核验 |

不要为了读取玩家私有数据默认复制到共享关卡实体；任意空模型也不自动变成这三个作用域可读取的数据库。

**变量表怎么定**（一行一个字段 ✓）：

| 列 | 说明 |
|---|---|
| 变量名 | 建议**统一前缀 + 中文**（如 `侦_名声` ✓）；⭐ 名字在**节点图里是数据** ✓ ⇒ **改名 = 静默失效** ✗ ⇒ 名字要**逐字**与代码一致 ✓ |
| 类型 | 整数 / 浮点 / 字符串 / 布尔 / **整数列表 / 字符串列表** ✓（列表能"一次带走一组" ✓ 省参数 ✓） |
| 谁写 | 一般**只有主控写** ✓（单一写者 ✓ 免得两个脚本互相覆盖 ✓） |
| 谁读 | 列全 ✓（每个读方都要有"提前布点"✓ 见 snippet） |
| 更新时机 | 变化时 ✓（**别每帧发** ✗ 会刷爆信号） |

**限制（真机核过 ✓）**：同一实体**不许重名** ✗ · 单实体运行时上限 **500** ✓ · 整数取不到 = **−2147483648** ✓ · 浮点精度 0.0001 ✓

**实例（《侦探杀》17 个变量 ✓ 全在关卡实体上）**：
`侦_时间`(整数) `侦_名声`(整数) `侦_消息`(字符串) `侦_比例`(整数列表) `侦_名单`/`侦_格文案`/`侦_线索`/`侦_事件日志`(字符串列表)
`侦_关卡`/`侦_剩余邪恶`/`侦_选中格`/`侦_详情态`(整数) `侦_关卡名`/`侦_犯罪现场`(字符串) `侦_技能义警`/`侦_技能裁缝`(布尔)

## Step 3.5 · 信号选型的**反面**（什么时候**不要**用"按类型设变量"）

> 来源：联动测试里，一个带技能的运行**自己推翻了"照抄模板"** ✓ —— 它给出了比本文档更进一层的判断 ✓。

⭐ 下面 Step 4 那套（**按数据类型建信号 + 节点图通用"按名字设变量"**）**不是万能模板** ✗ —— 它的前提是：

| 前提 | 说明 |
|---|---|
| **客户端是权威** | 单机玩法里主控在客户端 ✓ ⇒ 客户端算好 → 发信号 → 让节点图**替它写变量** ✓ |
| **变量只是"广播"** | 值由客户端决定 ✓ 节点图只做搬运 ✓ |

⇒ **一旦权威在服务端**（联机 / 反作弊 / 要服务器裁决 ✓）就**不该照搬** ✗：
- 变量应由**服务器节点图自己算、自己写** ✓（客户端只读 ✓）
- 客户端**根本没有 Setter** ✗ ⇒ 那条"按类型设变量"的信号链**没有存在意义** ✓
- **多一条通道 = 多一处契约错位点** ✗ ⇒ 能少就少 ✓

**判据（一句话）**：
> **谁算这个值，谁写这个变量** ✓
> 客户端算 ⇒ 客户端发信号、节点图搬运 ✓ ｜ 服务器算 ⇒ 节点图自己写 ✓ 客户端只读 ✓

**联机还要额外记得**（真机实测，别等做的时候才发现 ✗）：
- **纯客户端脚本之间的 `ServerSignal` 不互通** ✗ ⇒ 客户端无法自组网，一切同步必须过服务器 ✓
- **服务器 → 客户端信号延迟最低 ~100ms** ✓ ⇒ 手感类操作（拖拽 / 连招）必须"**本地乐观 + 服务器校正**" ✓，不能等回包 ✓
- **服务器节点图是编辑器里可视化搭的 ⇒ AI 够不到** ✗ ⇒ 联机方案里**节点图那部分要提前标成"只能创作者做"** ✓
  否则会撞上"**AI 推不到底**"的硬阻塞 ✗（这次评估就是据此判定"联机**不是偏好题、是架构分叉**" ✓）

## Step 4 · 信号清单（按"数据类型"建，不按字段 ✗）

**做法**：每个**数据类型**一条信号 ✓，参数固定 **`名称`(字符串) + `数值`(该类型)** ✓
节点图做**通用"按名字设变量"** ✓ ⇒ **以后加字段不用改节点图** ✓✓

```
侦_整数 / 侦_字符串 / 侦_布尔值 / 侦_整数列表 / 侦_字符串列表
（要"追加"语义再各加一条 `_新增` ✓ 但注意追加会累加 ✗ ⇒ 一般只用"覆盖" ✓）
```
⚠️ 五条必须做对的细节（参数顺序 / 目标实体=关卡实体 / 是否触发事件=是 /
客户端信号没有"事件源实体" / 列表只用覆盖 ✓）⇒ 详见 `blackboard-to-variable-signal.md` §3 ✓
