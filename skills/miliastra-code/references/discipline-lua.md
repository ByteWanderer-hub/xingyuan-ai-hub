# 千星奇域 · 工程纪律（执行 / 交付 / 需求 / 决策 / 风格）

> 与「铁律」分工：**铁律**管"代码怎么写、平台底线在哪"；**纪律**管"怎么接需求、怎么改、怎么验证、怎么交付"。
> 本域的纪律比别的域更要紧一层：**脚本是活文件（唯一副本、没有 git、没有撤销）**，且很多坑是"静默"的——所以"先确认、留证据、可回滚"不是流程洁癖，是防丢代码。

---

## 1. 执行纪律（怎么改）

- **改码前置确认**（三项齐全才动手）：
  1. 读目标文件（含头部版本块 → 知道它在哪一版、交接值是什么）；
  2. 查关联引用：`rg -n '<黑板字段名>\|<控件名>\|<挂载名>' <本次目标源码与必要调用方>`（本域改一个字段会跨脚本断链）；
  3. 冲突检查：目标是不是**构建产物**（**项目里**有 `tools/build-*.mjs` + 当前项目的源码片段目录）→ 是就得改片段。
- 用户只要审查时不修改；已明确要求排障修复、审计并修改或自动交付时，继续完成授权内工作，不另设开工审批。
- 覆盖活文件、玩法/存档变更、删除或外部发布按具体影响核对已有授权；不因一次改动达到某个文件数重复索要批准。写前保留备份、核对归属与指纹，并说明验证和回滚方式。
- 同一问题两次失败后换方法取证；只有改变目标/范围/权限或外部条件确实无法独立解决时才交用户决策，不把普通调试计数当停工条件。

- **批量防线**：批量改动前先 `miliastra_code op=backup`（每个脚本各备一份，永不自动删）；改完逐个过门禁，别"改 6 个文件只验 1 个"。

## 2. 交付纪律（怎么交付）

- **无验证证据 = 未完成**。可用的证据（按说服力从高到低）：
  | 证据 | 命令/来源 | 能证明什么 |
  |---|---|---|
  | deploy 回执 | `miliastra_code op=deploy`（SHA/字节/无 BOM/strict lint/备份路径） | 文件真的换了、结构合法、可回滚 |
  | 嵌入式一致性 | `miliastra_map op=script` 的 `match` | **游戏会跑的就是这版**（`match:false` 时试玩=白试） |
  | 运行时日志 | `miliastra_log op=runs`（`errorSample` / `首错=` / `faultMatched`） | 这局真的跑起来了、没崩 |
  | 模拟器 | `miliastra_sim op=verify` / `op=cases run` 的 `snapshot.logs` | 脚本跑没跑、控件建没建（**不等于真机**）；写时序用例时时间点用 `at`（绝对秒）显式给，`cases[].steps` 下的 `after` 实测会被忽略 |
  | 画面 | `miliastra_shot` / `miliastra_sim op=frames`（PNG + 帧间像素差） | 画面对不对、动效动不动 |
  | **逐帧字段**（动效/颜色/透明度） | `node scripts/frame-probe.mjs --config <配置.json>`（真 Lua 5.3 + 真 Tween 插值，逐帧打字段） | **渐入还是渐出**、"先亮后灭"、两个补间有没有抢同一批字段 —— 这些合成模板**结构上看不到**，模拟器一律拦不住 |
  | deploy 前交接值对比 | `node scripts/diff-live-config.mjs <我的源.lua> <活文件.lua>` | 创作者填在活文件里的模板索引**没被我覆盖**（照镜像 deploy 会覆盖回 0） |
  | 静态门禁 | `lua-check.mjs all --baseline` | 作用域与风格没退化（**不证明运行时**） |
  | **投递前总检**（插件侧，一次查完） | `miliastra_code op=preflight`（插件 **0.6.0+**，只读） | 从当前版本回执确认实际检查项与 `verdict`；不替代项目规定的独立作用域/风格/UI 门禁或运行时验证 |
  | deploy 自带的语法闸 | `miliastra_code op=deploy`（strict） | 0.6.0 起用 fengari **真解析** —— 以前只查括号/`end` 配对，所以"deploy 成功"≠"语法正确" |
- **交付前自查**：两道门禁绿 → `build-main`（若涉及片段）→ 模拟器无 `首错=` → 报告里写清"改了哪、为什么、证据是什么"。
- **证伪优先**：
  - 新建、修改门禁或有证据怀疑它无效时，用**负向用例**证明它会红（造一个新文件带 warn，看是否 exit 1）；
    ★ 更要防的是**门禁根本不存在**：2026-09-29 发现本技能引用了 15+15 次的 `tools/check-lua-scope/style.mjs`
    **全机都不存在**（原文指的是某个项目工作区）—— 于是"从来没红过"其实是"从来没跑过"。
    现在自带 `scripts/lua-check.mjs`，且它**自带 `--selftest`**：首次接入或修改后运行其自检；复用同版本有效结果，不每次重复跑。
  - 新写的检查器**必须配正反例**：正例证明"能命中"（本次：造一处 `local function` 声明在后 ⇒ 报
    `FORWARD_REF`，并在真 Lua 运行时复现 `attempt to call a nil value`），反例证明"不误报"（干净文件 0 命中、
    注释/字符串里的同名调用 0 命中）。**只有正例 = 可能是瞎报；只有反例 = 可能是空转。**
  - 断言串**从 actual 复制，不要手打**：2026-09-29 我把「推进=整行渐入」打成「盖行渐入」，模拟器如实报不匹配，
    白排查一轮。模拟器/探针都会回 `actual`，照抄它。
  - "控件建出来了" → 用 `count` 断言数出来，**不要**用"日志没报错"代替；
  - 关键算法/结论 → 先构造反例或对照（跑通 ≠ 正确）。
  - **断言必须"只可能由目标路径满足"**：同一动作若有多个来源，日志就要带**原因/来源**字段，
    断言只选那句唯一能证明目标路径的（例：`原因=停留到点` vs `原因=被顶掉`）。
    真实教训（2026-09-29）：断言只写了「出现『销毁提示条』」，而那句是被「顶掉最旧」打的 ⇒
    **假阳性通过**，缺陷一路漏到真机才暴露。破坏性动作（销毁/清理/停止）尤其要带原因。
- **没跑真机就写 `pending`**（证据双轴：`evidence_source` / `device_status`，见 SKILL.md §2）。

## 3. 需求澄清纪律（怎么接需求）

- **意图三分法**：① 信息查询（答完即止，别顺手改代码）② 简单任务（单点改动，直接做 + 报证据）③ 复杂任务（厘清相关架构与验收；已有明确方案和授权则继续）。
- **模糊需求转可量化验收标准**："手感好/不卡/好看" → 指标 + 正反例（如"按住方向键 3 秒不摔死"、"帧间像素差 > 0"）。
- **奇葩需求 / bug 里夹带需求** → 范围有实质歧义时用 `miliastra-bb`，只澄清影响实现的决定。
- **绝不替创作者简化**：他说要 4 关就是 4 关；拿不准先问。

## 4. 决策留痕纪律（怎么取舍）

- **反选论证**：多方案时说明「为什么不是备选」+ 接受什么代价（如"用控件黑板而不是全局变量：多一次 `GetChild`，换来跨脚本不互相踩"）。
- **撤销条件**：每个有风险的动作都要能回滚——快照（`miliastra_code op=backups` 列出全部备份 → `op=restore backup=<路径>`）、插件备份（`_backup/<名>.bak`）、`miliastra_code op=restore`。
- **复杂度豁免**：低复杂度、纯机械、行为等价的改动（`--fix` 一类）不必写长篇论证，**但要给前后数字**。
- **记录在哪里**：按当前工作区约定记录；小改在回复或既有记录说明，复杂任务复用主题文档。不自动创建报告、提交或推送。

## 5. 风格对齐纪律（怎么跟项目一致）

- **先取样再动手**：看同目录 1~2 个既有脚本的命名/注释语言/日志标签/缩进，跟它走（本域默认中文注释 + `[玩法/脚本]` 日志标签）。
- **配置优先**：有 `.editorconfig` / 既有格式化习惯就跟它；没有就按 `references/lua-style.md`（融合 LuaRocks / Olivine / Daedalic 并按千星现实仲裁：4 空格、双引号、camelCase）。
- **不为了统一重排全库**：规范约束**新代码**；存量要么不动，要么走 `references/style-remediation-workflow.md` 的**三步整改**（备份 → 摸底 → 分档）并留快照。
- **冲突处理**：外部风格指南 vs 本工程既有代码 → **既有代码赢**；平台约束 vs 任何风格 → **平台赢**（如 `assert` 引爆 vs 聚合故障块，选后者）。

## 附：2026-10-05 追加的三条 AI 作业纪律（真机实战换来的）

### 1. 批量替换报 `OK` **不等于**产物正确
- 替换脚本的 `OK` 只证明"原字符串匹配到了"，**不证明生成的 new 字符串是对的**。
- 实测事故：PowerShell 里写 `"...$nlRuntime..."` 时，`$nlRuntime` 被当成**变量名**（不存在 ⇒ 空）⇒ 换行丢失 ⇒ 两个状态位初始化被**粘成一行注释** ⇒ `attempt to compare number with nil` ⇒ `OnUpdate` 进 FAILED、**整块界面不显示**；另一次同因造成 `'end' expected` 语法错。
- **纪律**：① 拼多行用 `-join` 数组、元素用**单引号**，或写 `${nl}`（`$nl` 后紧跟字母会被吞）；② 改完**必须从产物里把那几行打印出来核对**。

### 2. 取证日志必须打印「**真正生效的那个变量**」
- 实测事故：在 `showFail` 里打日志读 `VIEW.actorSlotOf["CHILD"]`，而**染色实际用的也是同一个字段** ⇒ 日志里的 `nil` **就是根因本身**，却被当成"另一条线索"去查数据和登记代码，白跑一轮。
- **纪律**：日志要打印**赋值 / 判定所用的那个表达式**，并**同时打印它所在函数是否被执行**（否则分不清"没执行"和"值为 nil"）。

### 3. 用户截图上的**标注不是运行画面**
- 实测事故：把创作者 QQ 截图上的**手绘红框**当成了"我做的门高亮生效了"，并据此写下"✅ 已验证"。
- **纪律**：读用户截图时先分清"哪些像素是程序画的、哪些是人加的标注"；任何"我以为生效了"的结论必须能指到**程序写入的那一行** + **可复现的观察**，否则如实标 `pending`。
