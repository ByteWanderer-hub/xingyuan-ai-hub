## 客户端控件的动态创建（正式服实测，最重要的一课）

`game.InstantiateClientUIControl(controlPrefabIndex, parent)` **必须传 2 个参数**（少传报 `bad argument count … 2 expected, got 1`）。

**能不能创建，只取决于控件的「来源」，与它叫什么、摆在哪个父级下无关：**

| 控件怎么来的 | 能否被脚本创建 | 证据 |
|---|---|---|
| **在「客户端控件模板」库里【添加客户端控件】→ 存为模板** | ✅ **只有这种能** | `1073741867`(文本框) / `1073741868`(图片) 实测 `>>> OK` |
| 从控件面板直接摆到**客户端控件容器画布**上的实例 | ❌ 恒返回 `nil` | `1073741863~1866` 实测全 nil |
| **模板控件的子节点** | ❌ 恒返回 `nil` | 文档 §八「注意」第二条 |

文档原文（`docs/官方文档-7.1正式/原文/doc_客户端控件和客户端脚本.txt` §八）：
> 注意：仅存为模板的客户端控件，支持通过接口 `ClientUIBaseControl` 被动态创建
> 注意：挂载在主屏中的客户端控件，以及存为模板的客户端控件的子节点，均不支持通过脚本接口动态创建

**踩过的坑（别重犯）：**

1. **模板库空 = 对任何索引号都返回 nil。** 空模板库下扫过 276 个号、又按运行时 `prefabIndex` 逐个试，全部 0 命中 —— 白折腾一大圈。**动手前先确认「客户端控件模板」库里真的有模板。**
2. **编辑器面板显示的「索引」≠ 运行时的 `prefabIndex`**（后者才是官方字段表里的「控件模板索引」）。实测：面板 `1073741853/1854/1855` ↔ 运行时 `1073741866/1865/1864`，**两套号，不可混用**。
3. **别让人抄号**：运行时用 `game.GetClientUIControl(id)` 读活控件的 `prefabIndex`，或直接从 `.gil` 读 —— 但**读到的实例 `prefabIndex` 也不能创建**（见上表第 2 行），**只有模板区的号才行**。
4. **`.gil` 只反映已存盘的状态**：编辑器里改完不按 `Ctrl+S`，磁盘上还是旧配置。**改完必存盘，再谈验证。**

**标准验证流程（不靠猜）：**

```powershell

node tools\gil-clientui.mjs "<关卡>.gil"
# 2) 那些无 parent 的新记录 = 独立模板，其 id 就是可用的 controlPrefabIndex
# 3) 部署探针 / 正式脚本，试玩一局，看日志
```

### 按键事件（探针实测 + 文档抽取，两边逐项对上）

`script.object:AddKeyEventListener(ev, fn)` 只认 **`Enum.KeyEventType`**（164 项，键鼠+手柄都在这一张表里）。
对照表见 `docs/千星奇域_按键事件枚举对照表.md`。

| 要干的事 | 正确的枚举名 | 物理键 |
|---|---|---|
| 左右移动 | `KeyboardMoveLeftKeyDown` / `KeyboardMoveRightKeyDown`（配 `…Up`） | A / D |
| 前后移动 | `KeyboardMoveForwardKeyDown` / `KeyboardMoveBackwardKeyDown` | W / S |
| 跳跃 | `KeyboardJumpKeyDown` | Space |
| 方向键（双相在用） | `KeyboardCraftspersonKey36=↑ / 37=↓ / 38=← / 39=→` | ↑↓←→ |
| 交互 / 技能3 | `KeyboardInteractKeyDown` / `KeyboardCharacterSkill3KeyDown` | F / R |

**两条会静默出错的坑：**

1. **`Enum.KeyboardKeyCode` 里没有物理键名** —— 它只有语义键（`JumpKey` / `MoveLeftKey`… 共 59 项），
   所以 `Enum.KeyboardKeyCode.W`、`Enum.KeyboardKeyCode.Space` **恒为 nil，且不报错**。
   双相 v6/v8 的 `resolveKeyEvent` 把三张表都当候选试（`KeyEventType` → `KeyboardKeyCode` → `ControllerKeyCode`），
   实际**总是命中第一张**，所以没错 —— 但新代码别照抄这个「多表兜底」的写法，认准 `Enum.KeyEventType` 一张表即可。
2. **日志单条消息上限实测正好 10000 字符，超出部分静默截断**（不报错、不提示）。
   探针打 `Enum.KeyEventType`（164 项）时第一片就撞上限，
   `KeyboardMoveLeftKeyDown` / `KeyboardJumpKeyDown` 这些排在字母表后面的名字**全被切掉了** ——
   只看日志会得出「枚举里没有这个键」的**反向结论**。长输出必须分片打印。

## 坑记录：一个概念两个变量 —— 状态串的 `stage=` 来自 `G.phase`

**现象**：新写的标题画面脚本 `开始场景 start` 日志显示 `OnInit / OnStart / 就绪（黑板已找到）` 全部正常，
但**整局没有一句「标题画面 显示」**，画面一直是调查板。

**定位（靠日志，不是猜）**：
1. `miliastra_log op=runs` → 那局 52 条、**0 报错**，且 title/popup/codex 三个脚本的 OnInit/就绪都在 ? ? 脚本**跑了**；
2. `miliastra_log op=grep '阶段='` → input 从**第一帧**就是 `阶段=reveal` ? 状态串里的 stage 不是 title；
3. `grep '";stage=' 06_board.lua` → **`local txt = "stage=" .. G.phase`** ? **状态串的 `stage=` 取自 `G.phase`**，
   而新代码写的是 `G.stage` ? **写了个没人读的变量** ?

**修法**：新代码里的 `G.stage` 全部改回 `G.phase`（共 7 处：03_core 1 + 05_commands 6），并确认
`freshStart`（`06_board.lua:261`）的顺序是「先 `G.phase="reveal"` → 再 `initGame/initBoard(1)`」?
initBoard 里设的 `G.phase="title"` 在**之后**执行 ? 标题画面生效。

**教训（写进纪律）**：
- **一个概念只允许一个变量**。改状态机前先 `grep 'G\.<字段名> *='` 与**状态串写出处**（`writeState`），
  确认"谁写、谁读、字段名从哪个变量来"，再动手 —— 否则会出现"代码看起来对、日志里毫无反应"的静默失效。
- 判定"脚本有没有跑"和"状态对不对"要**分开取证**：前者看 `OnInit/OnStart/就绪`，后者看**状态串里的值**（`阶段=` 这类由 input/主控打印出来的行）。


## 坑记录：覆盖层「看不见」= 绘制层级 —— 创建顺序 + 越界的 `SetSiblingIndex` 静默无效

**现象**：《侦探杀》点「选择关卡」，日志里 `ui=title/pick` 切换、`jump` 目标都对（盲点都点中了第 7 关），
但**面板就是不在画面上**。连修两轮都不见效。

**平台事实（两条都必须知道）**：

1. **创建顺序 = 绘制层级：后建的画在上面。**
 真机证据不是猜的 —— `board.lua` 顶部创作者 的实测注记：
   「翻牌的文字看不到」＝角图建在文字之后盖住了字；「下一关按钮没了」＝结果面板建在按钮之后盖住了按钮。
   ⇒ 反向用法就是：**要盖在最上的东西，必须最后创建**。
2. **`SetSiblingIndex(index)` 越界不报错、返回 `false`。**
   官方 API 文档原文：`index 范围是 0 到父控件的子控件数量减一`。
   我传了 `9999` ⇒ 越界 ⇒ 返回 `false`、**不抛异常** ⇒ 只 `pcall` 看"有没有抛错"的写法**静默失效**
   （日志里一个字都没有，画面也没变化 —— 最难查的一类）。
   **正解是 `SetAsLastSibling()`**（同级末位）；判据用 **`ret ~= false`** 而不是 `ret == true`（防某版本返回 nil）。
   兜底可以自己算末位：`ROOT:GetChildren()` 数量的 `n-1`。

**跨脚本的额外一层坑**：覆盖层由 `表现 view` 建，但日志顺序是
`[view] 界面已建` → `[board] 调查板已建` ⇒ **board / reveal / fx 的控件都是 view 之后建的**。
所以在 `build()` 里提层、甚至"在 build 里创建"都没用 —— 一定要**等别人建完再创建**。

**落地口径（可直接照抄）**：
- 覆盖层控件**不在 `build()` 里建**，改成"第一次要显示时"创建（`buildOverlay()` lazy）；
- 创建**再延后一帧**（`tickN >= 2`）：view 与 board 的第 1 个 `OnUpdate` 在同一帧里，只有第 2 帧才保证 board 已建完；
  第 2 帧由 `tick` 强制重画一次（状态串没变也要重画），否则"按状态串变化才渲染"的写法会让覆盖层永远建不出来；
- 每次模式变化 + 每 0.4 秒再 `SetAsLastSibling()` 一遍（两条规则都兜住）；
- 提层成功/失败都要**打日志带数字**：`覆盖层提层：pick 共 17 个，失败 0`。

**模拟器判不了这一条**：模拟器出 PNG 时把"图片"与"文字"分两遍画，
所以**它画面里的文字永远在任何图片之上**，与真机的创建顺序无关 —— 层序问题只能真机看。

**另外（工具侧踩到的）**：`miliastra_code op=deploy` 只给 `source`、不给 `file` 时，
目标活文件是**按"最近改动"挑的**，不是按 `source` 的文件名 ——
实测把 `交互 input.lua` 的内容写进了 `表现 view.lua`（回执里 `dest` 明写着，但很容易不看）。
⇒ **多脚本工程一律显式传 `file="<活文件名>"`**，并且看完 `dest` 再往下走。

**顺带一条 UI 坐标口径（同轮踩到）**：`表现 view.lua` 这一系的 `y` 是**从屏幕顶部往下数**的
（`toY(dy) = canvasH/2 - dy*sy`，HUD 用 `y=56` 落在顶部即证）。
按"从下往上"的直觉写覆盖层，出来的面板会**上下颠倒**（标题跑到最下面、关闭按钮跑到最上面）——
本轮选关面板就整块反了一次。改 `view` 的 `add(...)` 坐标时，**必须同步改 `input.lua` 里对应的热区矩形**
（两者是"画在哪 = 点哪算"的硬契约；本次已用 `tools/check-ui-contract.mjs` 逐字比对过 13 个按钮槽 + 12 行）。

**`game.GetCursorUIPos()` 的确切口径（真机踩坑后改正 —— 本文先前写反了）**：
它返回的是 **"画布左下角原点"的像素坐标**（与 `CursorEventData:GetUIPos` **同一族**），
**不是** `view.lua` 那套"顶部原点 + 1000 高设计空间"。⇒ 要拿它去比设计坐标矩形，必须先换算
（换算与本工程 `input.lua` 的点击回调**逐字一致**）：
```lua
local dx, dy = ux / sx, DH - uy / sy     -- DH = 1000；sx, sy = 画布 / 设计稿(1600×1000)
```
**真机证据（写反的原因与纠正）**：`view` 的悬停高亮漏了这次换算 ⇒ 创作者实测「鼠标停在【继续】，
高亮却在【角色图鉴】」——纵向被镜像，正好偏 2 行。修正后模拟器复测：光标停在【继续】(
注入 800,547) ⇒ 日志 `[侦探1/view] 悬停 → mxB1`（继续）✓。
（此前那条"点角色图鉴命中 T_CODEX"的"证据"用的是 `data:GetUIPos()` **经 input.lua 换算后**的值，被误当成了 `GetCursorUIPos` 的原始返回值。）

**模拟器里点按的坐标口径（复测纠正）**：`op=verify` 的 `click:{x,y}` 与 `op=play action=pointer {type:"click"}`
**是同一套**：吃**左下原点、按画布高度**的坐标 —— 和上面 `GetCursorUIPos` 的原始口径同一套
（引擎内部才会换算成设计坐标去派发 CursorEventData）。
⇒ 1600×900 画布上要点设计坐标 `y`，注入值 = **`900 − y×0.9`**（例：点设计 y=780 → 注入 198 ✓）。
（本文早先写的"`play.pointer` 原样透传"是**错的**：实测注入 277 → Lua 读到 692 = `(900−277)/900×1000`。）
两者混用时"明明点对了却没反应"就是这个换算没做。

## 坑记录：覆盖层状态 `ui` 只能由一处写 —— `initBoard` 写它 = 点了没反应

**现象（创作者真机 4 条反馈里的两条）**：「开始调查点了没有用」「选完关回标题页」。

**真因（代码级，不靠猜）**：`initBoard()` 里写了 `G.ui = "title"`，而 `start` / `jump` 处理器是
`先 G.ui = "" → 再 initBoard()` ⇒ **刚清掉的 ui 又被设回 "title"** ⇒ 标题覆盖层不消失。
另外 `pick` 的关闭是硬编码 `G.ui = "title"` ⇒ 玩着点开选关再关掉，被丢回标题页。

**修法（写进纪律）**：
- **一个字段只允许一个写入方**：`ui` 只由命令层（`start`/`jump`/`pick`/`codex`）与 `freshStart()` 写；
  `initBoard()` 这类"重建棋盘"的函数**不许碰它**（它被 4 条路径调用，写进去就是 4 个隐藏的覆盖源）。
- 覆盖层用 **"记住从哪来"** 而不是硬编码去向：打开时 `G.uiBack = G.ui`，关闭时 `G.ui = G.uiBack or "title"`。
- 每次切换都 `log("覆盖层 → xxx；关掉后回 xxx")` —— 真机再遇到"点了没反应"，这一行直接给出答案。
