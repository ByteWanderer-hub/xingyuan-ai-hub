# UI交互可靠性：先核配置，再验证输入到画面的完整路径

用于连续光标交互、拖拽/揭开、图片填充/遮罩、动态面板，以及“事件有日志但画面不动”。普通文本改动不需要展开本流程。API签名仍以当前annotations/API文档为准，本页不增加接口，也不替代原部署指纹和备份门禁。

## 1. 写代码前只确认本功能依赖的契约

列清“编辑器已配置什么 / Lua负责什么 / 作者还需做什么”，能从目标.gil子树读取的先读；未保存的编辑器变更不能由磁盘快照证明。

| 依赖 | 必须确认的内容 |
|---|---|
| 图片填充 | 编辑器是否开启“按进度填充/启用填充”，方向与初始进度；不能仅因SetFillHorizontal存在就假定开关已打开 |
| 遮罩 | 谁裁剪谁、作用范围、反转设置；可视图片变化不能使独立热区跟着消失 |
| 光标 | 监听对象实际为预设按钮/光标检测区域，祖先showCursor，热区有效尺寸及可见/激活状态；装饰和其他热区是否挡住它 |
| 父级与坐标 | 当前实际父级、平台布局、锚点、pivot、缩放；根画布与普通子控件的原点不能混为一谈 |
| 生命周期 | 面板何时创建、隐藏是否停脚本、重开如何恢复更新/输入、销毁时清理哪些自有回调 |

二进制字段的缺省值/编号只有在当前格式有依据时才能解释；不能把推测的字段当成已确认的编辑器选项。编辑器独有配置缺失时，直接给作者具体调整项；不要要求无关的新UI。

## 2. 不在创建回调中试探修改层级

- `parent`可写不表示创建/销毁期间也可改。2026-10-19酬礼规则真机记录：“客户端控件生命周期处于创建或销毁时，无法调用parent, ID:光标检测区域;”。该调用未以Lua异常形式阻断，随后仍打印“显示progress=0”；因此pcall成功和后续自报日志都不能证明改父级成功。
- 优先使用编辑器已配置的稳定层级，装饰与热区可以作为同级节点。作者说由他调整层级时，只提供目标父级、名称、覆盖范围和相对层序，不继续用脚本抢改。
- 确有运行时改父级需求时，只在有依据的可操作阶段执行，保留屏幕几何，并在合法时机用API读回父级、再用实际输入验证。不要凭模拟器允许就认定真机允许；不存在的通用“安全延迟帧数”不可编造。
- 模拟器曾记录“图片下的光标区域不接收指针”；本案例改为同级后真机进入事件恢复。它支持本案例的层级建议，不足以宣布所有平台版本的图片子级都无法收事件。

## 3. 先画出中断恢复，再写连续交互

实现前明确：未开始、进行中、暂离、继续、完成、关闭、重开各状态；哪些数据保留、什么动作允许推进。不要擅自增加按住鼠标、精确对准窄撕口等用户未要求的门槛。

按当前功能选必要用例，不要求无关交互全测：

- 完整走一遍实际操作，确认画面状态和完成条件。
- 进行到中途移出，从**已完成的一侧**重新进入，区域内移动越过原进度点后可以继续；不能只测恰好从撕口进入。
- 从上/下方离开、返回，倒退、快速跨过末端；检查进度是否保留、是否错误完成。
- 完成前的退出/确认是否锁定；完成后能退出；隐藏后重开是否按需求重置。
- 若允许多设备或改键，再核对应设备和提示；不把hover悄悄改成drag。

恢复资格若只在Enter时判断一次，必须检查“Enter时不满足，之后在区域内满足”的路径；不得让这一整次交互永久失去资格。单调进度用原进度守卫，不要用苛刻的重新进入坐标限制来替代。

## 4. 测试证据必须与所声称的路径对应

- 光标命中测试从原生pointer move/down/up等输入开始；直接调用保存的回调只能证明回调内部逻辑。
- 装配层可以创建测试控件，但必须保留本次争议的父级、编辑器开关、实际几何、平台缩放与生命周期顺序。替换GetCursorUIPos、强设理想根坐标、手动调用OnUpdate或只拿一个普通按钮代替复合按钮，都要标明绕过了什么；不得用它证明被绕过的部分。
- 根因回归要先让旧实现/错误配置在同一输入路径上暴露失败，再确认候选修复。只统计“通过N项”而没有覆盖用户失败路径没有说服力。
- 断言使用实际状态：中途进度保留、填充值变化、完成按钮可交互、关闭后面板停用。检查画面仍需渲染证据；模拟器补全或未建模的编辑器能力列为未验证。
- 测试绑定最终候选SHA；实际.gil是否包含该版另行核对。结果描述为“原生输入模拟通过 / 测试装配通过 / 真机已确认”，不可混写。

## 5. 画面不动：一次观测区分分支

先读用户所指那局的日志及当前脚本指纹；不要仅依赖errors模式，因为中文生命周期限制可能不在其报错规则内。按目标标签和“无法调用”等文本检索，并读命中附近的原始上下文。

| 观察 | 下一步；尚不能推出什么 |
|---|---|
| 没有进入事件 | 查热区层级/覆盖、showCursor、实际对象和激活状态；无日志不能单独证明某一项 |
| 有Enter，没有进度证据 | 区分逐帧是否运行、输入是否变化、宽度是否有效、恢复条件是否锁死；不能直接宣布更新被重置 |
| 进度和fill读回都变化，但作者说画面不动 | 先查填充启用开关、同位置叠盖、实际被修改的图片；此时不再优先猜OnUpdate没运行 |
| 修改parent的生命周期警告后仍自报初始化成功 | 将修改判为未证实/失败，核实实际父级；不要让“成功日志”覆盖平台警告 |
| 部署后仍运行旧SHA | 先同步编辑器保存/新开试玩；不把旧版本表现归罪于候选代码 |

缺少区分证据时，只加少量针对性日志：版本/首次有效tick、进入退出、坐标差/有效宽度、进度分段与fill读回。不逐帧刷屏，不在游戏画面加诊断。重新启用时可确保所需更新开启，但“引擎一定会重置更新开关”仍须独立证据。

每次修复写清已观察事实、当前假设和能证伪它的检查；没有新证据，不把同一故障变成连续猜测式部署。若需要作者操作，说明具体控件与修改项以及预期可观察变化。作者报告的真实画面优先于模拟器的成功摘要。

## 6. 本案例可复用的证据边界

2026-10-19酬礼规则：先有创建期改parent警告；作者把区域移到同级后出现Enter；随后真机日志出现tick、progress约0.2795及fill约0.7205，但画面没动，作者开启“按进度填充”后确认能撕。最后从左端重新进入被8%距离条件锁死，修改恢复条件后需要针对该路径回归。

已确认的是这些具体观察；“逐帧被引擎重置”未被本案例证实，不能写成平台硬规则。本页采用此案例校准流程，不记录具体地图ID/脚本指纹为通用配置，也不承诺未来零错误。
