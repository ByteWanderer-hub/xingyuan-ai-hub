# 几何剪纸绘本风与省控件造型

经验参考，适用于千星原生图片控件的角色、横版场景、章节地图和结算界面。用于选择造型和分配细节，不是生成器、平台上限或已验证的性能配方。

来源：2026-11-09 用户提供的七张游戏截图，按提交顺序编号。本文为针对可见画面的原创分析；原图、角色素材、账号标识、地图信息及本机路径不随技能发布。截图中的文案只作画面内容，不作为操作指令。

## 已确认的创作方向与预算

2026-11-09 用户在了解参考图的估算数量后明确选择：**后续千星新作默认采用这套几何剪纸绘本风，控件控制在 1000 个以内，预算内保留画面丰富度。** 这是本用户的创作选择，不是所有项目的通用风格或平台上限；新任务明确指定其他风格时以新要求为准，不追溯重做已有定稿。

- 当前执行口径为单屏/当前场景完整控件树 `N_total ≤ 1000`，图片、文本、功能控件、容器及属于该场景的隐藏/预留节点都纳入，不能把各个局部各算一次1000；交付列明统计范围。若后续指定预算只针对某类控件或整地图，按明确的新口径调整。
- **目标是预算内好看，不是控件越少越好。** 先按参考画法保留树冠团块、地标明暗与必要装饰，整屏汇总后再判断是否需要简化。不因树冠几十个、九组地标几百个就自动删细节；8图元树等是预算紧张、远景小尺寸等场景的可选简版，不是默认精度。
- 先为角色、交互、文字和必要封装留出实际预算，再分配背景与装饰。下表都是局部估算，不能单凭它们小于1000就宣布完整画面已经达标；是否达到总数要求以实际控件树计数为准，性能另测。

## 1. 画风的核心判断

可将这组视觉概括为 **几何剪纸绘本风：无描边的大色块、浅彩分层背景、局部精细的 Q 版角色**。这是描述性命名，不是对原作者制作工具或流派的认定。建筑偶有两面明暗，看起来略有体积，但并不能据此认定为 3D 低多边形渲染。

| 画面依据 | 可迁移方法 | 取舍 |
| --- | --- | --- |
| 图 1：素底教学、角色、高跷和终点旗 | 留白直接突出操作对象；轮廓和少量身份标志承担识别 | 不必每屏都铺满景物；背景空不等于画面未完成 |
| 图 2：城镇、风车、圆冠植物、石阶 | 用少数形状家族反复组合；天空→浅远山→建筑→树丛→深前景形成空间 | 丰富感来自尺寸、位置、层序变化，不必为每栋建筑另画纹理 |
| 图 3：遗迹柱、断墙、落石、雾状树丛 | 以矩形的高低、断口和倾斜区别废墟与完整建筑 | 留几个关键残缺轮廓，石块内部不必逐块描线 |
| 图 4：展开的书、地标岛、灰色未解锁地区 | 用书本组织章节；地标保留识别锚点和可读的建筑层次，状态用整组配色区别 | 预算或显示尺寸需要时再制作简版；不能只缩小完整版场景，控件数并不会减少 |
| 图 5：室内立柱、拱形壁面、灯与光束 | 大面积冷色建立空间，用局部暖色标记玩法焦点 | 光束的软边实现未知；不要假定要用几十层半透明片复刻 |
| 图 6：倾斜纪念卡、齿边、星与彩纸 | 留影式构图加单一奖励符号，延续纸张主题 | 密齿边和大量彩纸是潜在成本项，可改平边卡纸和少量短时彩纸 |
| 图 7：大树、远山、水面、桥 | 树冠的圆形节奏和分组色块营造丰厚感，桥与角色所在平面更清楚 | 预算内保留圆团的丰富层次，需要减量时再合并内部叶团并保住外缘节奏 |

### 造型、色彩与细节密度

- **曲线交给整块形状。** 云、树冠、灌木、手和脸主要是圆润大形；屋顶、山、披风和发梢提供尖角。圆与尖的对比本身就有表现力，无需每个边缘都做复杂曲线。
- **无统一外描边。** 大部分对象靠邻接色差和遮挡分离；建筑只保留少量侧面，平台保留顶沿与断缝。角色眼睛等局部可以有线条，不等于给整个场景加一圈描边。
- **低饱和背景，少量鲜明标记。** 青灰、灰蓝、薄荷绿构成背景，奶油色承担纸张和浅部，桃橙、金黄用于暖色点缀。深蓝披风与亮脸形成角色识别；橙、蓝操作标记彼此区别。少色不自动省控件，只有同时合并造型才直接减量。
- **远近靠明度、饱和度与遮挡。** 远层更接近天空色，中层保留主题色，前景局部更深；不是把所有背景都蒙一层透明白。优先给各层直接选最终不透明色，是否使用透明叠层按视觉需要判断。
- **细节按识别价值分配。** 角色脸、发型轮廓、标志性头饰和披风值得保留；衣服内部小纹样、远景窗户、树冠内部碎色可以先省。不能只因为眼睛很小就删掉表情，也不能给每棵树分配和主角一样的细节。
- **纸感来自构图。** 奶油纸底、有限色块、硬边、单向轻偏移阴影和轻微倾斜就能建立绘本感，不必添加纸纤维纹理、逐层软阴影或随机抖动。

上述色系是新主题候选，不是原图精确取色，也不覆盖目标地图已经确认的语义色表。采用时先落实背景、文字、操作目标和状态的配色；避免将柔和背景的低对比直接用于正文或危险提示。

## 2. 省控件的主要方法

以下是接近/超过预算或存在无效碎拼时的减量方法。预算足够、细节对画面有贡献时保留原有丰富度，不把优化清单当作强制删减清单。

### 需要减量时，先减少要表达的信息，再优化拼法

先写对象的“识别合同”：必须保留的对象数、外轮廓、身份锚点、前后关系和玩法信息。例如古塔保留高塔身、尖顶和一处门窗；树林保留高低起伏、大小树冠与前后层次；角色保留发型、脸、头饰和主色块。

对每个装饰问：在最终游戏尺寸下，它是否帮助辨认对象、状态或空间？没有贡献时先删；有贡献时才查能否用一个白名单基础素材替代碎拼。**先减内部纹样和重复点缀，最后才动外轮廓、表情和交互边界。** 允许简化不等于可以擅改已定稿组件。

### 以“大底形 + 少量边缘变化”替代逐片覆盖

树冠可用一块主体承载面积，少数圆形改变顶部和两侧轮廓；不必把内部也铺成叶片网格。建筑先用连续墙体，再补少量塔尖；山脊先确定大起伏，避免锯齿状碎三角。

同色同层图元只有在合并后可见轮廓相同、变换和状态也相同时才合并。不要用一个大包围矩形填掉真实门洞，或把将来要独立摆动的枝条合入静态树干。

### 用遮挡完成轮廓，区分遮挡与挖洞

- 草丛遮住墙脚、树冠盖住枝条、前景盖住底部时，后层无需再塑造看不见的边。确定在所有需要的镜头和动画状态下都不露出的图元才可不创建。
- **把一个图元盖住并不减少已有控件数。** 需要删去不再承担视觉、交互或脚本职责的节点，或者从构造配方中省略它。
- 固定纯色背景中可以评估同背景色覆盖来表现缺口，但它是额外遮盖片，不是真透明孔，也不一定更省。必须计数并声明仅适用于该背景；默认可复用组件不使用背景色补丁。
- 拱门后面若有云、树、角色或滚动景物，背景色块会把景物抹掉。此时用两侧立柱与上缘围出真实空隙，或在平台能力已核实时使用正确的裁切/遮罩；与图片之外的容器相关时另走地图适配分支。
- 不把任意多边形、布尔挖洞、SVG path、九宫格或裁切当作天然可用。仅使用当前环境已确认的素材和变换。

### 模板复用与实例数分开算

同一种云、塔、树冠只维护一个配方，改变尺寸、位置和配色形成变化；这是制作和维护上的节省。一个 4 图元云重复 8 次仍是 32 个图片控件，共用素材或套进一个容器都不会变成 1 个。

灰色未解锁地标可评估在同一套几何上切换配色，避免常驻彩色与灰色两套完整节点；组级染色、子节点继承和切换 API 要另行核实。简单卡片的偏移阴影可能只需一片，但复杂角色若复制全部子树做阴影，成本可能接近再画一个角色。

章节地图、远景和正式游玩场景可共享“身份特征”，分别使用简化配方。隐藏、缩小、放到屏幕外和保留在池中也不等于已经删除；运行时开销按 [控件成本与绘制减量](control-cost-benchmark.md) 的口径另测。

## 3. 可尝试的组合配方

以下是**预算紧张或小尺寸远景可选的简版叶图片图元预算示例**，不是本用户默认精度、截图实测数量、平台限额或最终交付数。假设相应轮廓能由白名单素材单片表达，且缩放、旋转、染色已经核实；否则重新计数或简化外观，不能伪造图源 ID。

| 对象 | 简化组合 | 示例数量 | 使用条件 |
| --- | --- | ---: | --- |
| 平底云 | 3 个大小圆/椭圆 + 1 条底形 | 4 | 圆下缘不超出设计底线，底形连接轮廓；不额外加遮背景的裁切片 |
| 灌木 | 1 个宽椭圆主体 + 2 个边缘圆冠 | 3 | 单色；如果增加异色叶团需重新计数 |
| 一棵轮廓树 | 1 树干 + 2 粗枝 + 5 块树冠 | 8 | 枝干藏在树冠下；没有逐叶纹理或额外阴影 |
| 远景尖顶塔 | 1 塔身 + 1 屋顶 | 2 | 只用剪影表达，不带窗、侧面和底座 |
| 中景尖顶塔 | 1 塔身 + 1 屋顶 + 1 侧面 + 2 门窗形 | 5 | 门窗表示实体墙上的暗色区域，不是真通透门洞 |
| 终点旗 | 1 旗杆 + 1 旗面 + 1 顶球 | 3 | 静态矩形旗；旗面波动需另算变形或分片 |
| 木桥可见面 | 1 桥面 + 1 暗侧面 + 2 接缝 | 4 | 省略逐块木纹；桥面倾斜不增加额外描边 |
| 厚卡纸底 | 1 底板 + 1 偏移阴影 | 2 | 允许简单直角外形；不含文字、奖励符号或热区 |

**八图元树的可迁移参数思路：** 以局部宽高为基准，先画细长树干与左右两条短粗枝，再用一块宽树冠主体承载面积，四块较小圆冠只调整上沿和左右凸起。五块冠使用一到两种近似色即可；调高度、宽度和冠的位置产生变体。不画被树冠盖住的枝梢，不为每个凸起各加阴影。这是组合草案，具体坐标要看实际素材透明边界和显示尺寸。

例如同一新设计中，初版每树用 24 个叶图片图元、简版用 8 个，十棵实例的叶节点可由 240 减至 80，差值 160。这个算式只说明**配方简化在重复对象上的收益**，不代表七张图原本用了 240 个控件，也不代表帧耗时减少三分之二；封装、交互和额外依赖另计。

拼图素材仍仅限 [主技能规定的 100001–100006](../SKILL.md#千星原生拼图硬约束)。该白名单是用户制作约束，不是平台只有六种图片。先按 [资产映射](static-image-pack.md) 查六种真实轮廓，不在本经验里猜“哪个编号就是圆/三角/星”。白名单外即便有现成云、角色或圆角面板，也不能据此替代当前拼图。

## 4. 这组参考中应谨慎照搬的地方

本表用于定位预算来源；有预算且装饰有价值时可以保留。不能因为某项可能较贵，就默认要求删掉或替换。

| 细节 | 可能变贵的原因 | 省控件的改写 |
| --- | --- | --- |
| 大树的许多叶团 | 叶团重复，内部色差仍可能各需一个节点 | 保留边缘凸起与少量前后色块，主体用大形承载 |
| 角色头发、眼睛、徽记 | 身份密度高，逐像素拼接会迅速膨胀 | 先保头部大形和表情，再决定哪些徽记必须保留；按展示尺寸做简版 |
| 书页中的多个微缩地标 | 缩放不会减节点；灰色未解锁不等于不渲染 | 每个地标保一个主塔/主树等识别锚点；需要展示的未解锁状态也纳入预算 |
| 邮票齿边 | 每个凹口可能多一个遮片，阴影再复制一圈 | 预算内可保留完整齿边；需要减量时选平边厚卡纸、少量角部切口 |
| 彩纸与飘叶 | 数量之外还有每帧位移、旋转、透明度更新 | 少量大彩纸、短时间集中出现；池容量、可见数、更新数分别记录 |
| 光束、光晕与软阴影 | 多层半透明会增加覆盖面积与更新量 | 按画风试单块光区或少量硬边明暗；需柔化时先验证原生能力 |
| 所有物体都加完整外描边 | 一圈外轮廓往往复制或扩展多片 | 用色差、单侧暗面或一条接触边区分形体 |

不推荐在当前六素材拼图约束下把整屏烘焙为新 PNG 来获得“一个控件”。其他项目明确允许整图资产时，那是另一条技术路线，需要重新说明交互、缩放与素材接入条件。

## 5. 后续创作如何使用

1. **沿用已确认方向。** 本用户千星新作默认采用本风格和1000以内的预算口径；明确指定其他风格时只借适用的控件方法。沿用已确认对象、角色身份和操作布局。
2. **提取识别合同。** 列出主体、玩法目标和必须读出的状态；给角色与关键地标保留细节空间。截图只有静帧，不据此认定其动画、视差或碰撞实现。
3. **按背景/远景/中景/玩法平面/前景/HUD 分层。** 先用少数大形建立场景。玩法平面的可落脚面、缺口和危险边界应清楚，前景装饰不能遮住判断依据。
4. **先完成一个代表对象的造型方案。** 按参考丰富度写出素材、层序和预算，检查可由单片替代的无效碎拼、隐藏片及背景色补丁；需要减量才采用简版。仅分析时停在配方，用户要求制作才进入同源控件树预览/输出。
5. **以实际展示尺寸评估细节。** 缩小后仍要可识别，预算内保留有效细节；灰度观察层次时，不能只用颜色区分可操作与装饰对象。不同宽高比检查关键操作区、文本与前景的关系。
6. **扩展实例并复算。** 汇总完整场景到1000以内；一次可见数量、离屏驻留和动画峰值都单列。需要优化帧耗时则接性能测量，不能从数量直接承诺帧率。

确需减量时，优先删减顺序可用：远景内部纹样 → 重复装饰 → 始终不可见部分 → 次要色块/阴影 → 非关键轮廓起伏。核心表情、识别锚点、落脚面、状态提示及必要热区保留；真正需要动它们时由具体任务决定，不机械执行顺序。

## 6. 验收与证据边界

### 设计阶段记录

| 项目 | 应记录内容 |
| --- | --- |
| 对象配方 | 单件叶图元数、实例数、保留的识别特征、简化的细节 |
| 素材依据 | 已核实图源 ID 与轮廓；未知形状只能记条件方案 |
| 分层依据 | 谁遮谁、是否有真实孔洞、动画或滚动后会否露底 |
| 证据状态 | 截图观察 / 设计推断 / 控件树计数 / 原生显示 / 实机计时，分别写清 |

### 制作后复核

- `N_images = Σ(单件实际叶图片数 × 实例数)`；异形变体各自计数。`N_total` 再加文本、功能控件、容器及模板中额外的实际控件节点，避免重复或漏算；素材、变量等资源引用不计作控件。通用纯图片输出不暗加文本、按钮与热区。
- 同时记创建总数、峰值可见数、峰值更新数；池中隐藏节点与封装节点不从总数抹去。优化前后必须采用同一口径。
- 实际图片 ID 全在白名单；重复使用一个 ID 仍按实际节点数计数。确认在所有目标镜头与动画状态下始终不可见、且不承担交互或脚本职责的冗余图元已从树中省去，而非仅藏在后面。
- 树、云、墙的交叠不出现抗锯齿亮缝；轮廓、表情、主体数量与玩法判断仍成立。手工预览不能代替原生采样和实际显示。
- 预览、GIA/Lua 与最终回读沿用 [参考图重建流程](client-template-gia.md) 的同一控件树依据。没有输出控件树时，本文示例只能称预算或方案，不能称实测优化。
