## **十一、错误边界、日志与证据口径**

- 如果同一个故障连续三次修复尝试都失败，停止继续修改，回到 10\.1\.1 重新分类，并把证据缺口明确列出，必要时按第五节向用户索取缺失事实。

### **11\.1 验证知识与证据口径**

#### **11\.1\.1 验证知识**

|层|能证明|不能证明|
|---|---|---|
|静态检查|语法、作用域、明显 API/subtype 错误|编辑器真实行为|
|子 Agent 语法检查|能否被解析、明显拼写差异|编辑器 API 正确性，也不能证明故障已修复|
|日志块清洗|错误码、阶段、traceback 与出现次数|根因|
|对照已有 Demo 的量测|涉事元素的相对位置、尺寸与锚点归属的设计意图|编辑器最终显示结果与命中范围|
|本地逻辑复现|纯 Lua 计算类故障的根因|编辑器 API 与真机行为|
|模拟器内确定性复现（`miliastra_sim`）|脚本在引擎语义下跑不跑得通、控件建了几个、帧间像素差|真机渲染与素材、联机、性能与手感|
|真机最小探针|单项编辑器约束|完整玩法|
|场景测试|真实交互和画面|所有故障分支|
|故障注入|失败收口和半初始化安全|正常画面保真|

证据来源 `evidence_source`：

- `documented`：当前 API 文档明确写出。

- `provided_unverified`：用户、子 Agent 或已有文件提供，但尚未在真实运行环境核对。

- `observed`：已经在真实编辑器或游戏运行环境直接观察到。

- `inferred`：根据代码或静态检查推断；不能代表真机结果。

- `unknown`：没有足够证据，或现有证据互相冲突。

真机状态 `device_status`：

- `passed`：已在真实编辑器或游戏运行环境验证并通过。

- `failed`：已在真实编辑器或游戏运行环境验证并失败。

- `pending`：需要真机验证，但还没有执行。

- `not_required`：该结论不需要真机验证。

#### **11\.1\.2 报告约束**

记录重要结论时，必须同时填写 `evidence_source` 和 `device_status`，不得把它们混成一个状态。

```Plaintext
API 文档已经写明，但尚未真机运行：
evidence_source=documented
device_status=pending

子 Agent 返回的日志条目、语法检查结论或图片匹配结果：
evidence_source=provided_unverified（或 inferred）
device_status=pending

模拟器里复现出来的行为（`miliastra_sim`）：
evidence_source=observed（仅限"模拟器里确实如此"这一事实）
device_status=pending（真机仍未验证）

本地逻辑复现出的纯 Lua 计算错误：
evidence_source=inferred
device_status=pending（本地复现不等于编辑器内复现）

已经在真实运行环境验证通过：
evidence_source=observed
device_status=passed
```

`pending` 只是真机状态，不是证据来源。任何一层通过都不能替代其他层；不能把静态检查、子 Agent 报告或本地复现写成真机通过，更不能把“现象没再出现”直接写成根因已消除。

### **11\.2 在错误边界收口编辑器日志**

先从当前 API 文档确认普通、警告和错误日志入口的准确名称、调用形式、参数和副作用。不得因为旧 README 或旧代码曾使用某个日志函数，就认为当前版本仍然存在或行为相同。无论错误日志入口是否会自动抛错，致命错误都由 Runtime 明确进入 `FAILED`、停止输入和加载、停止逐帧逻辑并回滚已登记资源。

日志先形成结构化记录，再一次性输出有界连续块：

- 正常启动或阶段完成只通过当前文档声明的普通日志入口输出一次汇总，禁止按字段分开打印。

- 可恢复异常按需要通过当前文档声明的警告入口输出一次；相同问题必须聚合计数，禁止逐帧重复。文档没有独立警告入口时，不得凭空调用常见名称。

- 每个主故障只通过当前文档声明的错误日志入口输出一次，并使用 `GAME FAULT BEGIN/END <错误码>` 包住完整连续块；第一个主错误决定错误码和 traceback，后续清理错误只能追加，不能覆盖首错。

- cleanup errors 先收集，最后追加到同一个故障块；禁止在清理循环中逐条打印。

- 没有新增高价值信息时，不得让同一故障在后续帧再次输出。

需要用户提供诊断信息时，只请求对应错误码的完整 BEGIN/END 连续块，或直接请求一份编辑器日志文件；不得让用户逐条复制十几行日志，也不得来回搜索多个关键词。

只在当前 API 文档声明的启动、逐帧更新和清理入口等完整事务边界建立错误边界；受保护调用和 traceback 能力也必须先确认运行环境支持。不要给每个 getter、setter 或纯 Lua 内部函数单独套保护调用。**事务边界的正确用法是“捕获后立即进入 ****`FAILED`****、停止后续逻辑并输出一个聚合故障块”；把捕获结果吞掉并继续执行属于被禁止的绕过，两者不得混为一谈。** 如果编辑器日志无法取得，一次性向用户索取可用的日志导出方式或日志文件；取得日志前不要声称诊断已经完成。

**修复时的边界**：允许在诊断开关开启时增加聚合记录，但必须登记并在报告中说明；禁止把临时日志在正式版本中留存，也禁止用日志把报错“淹没”掉。

### **11\.3 使用 API 无关的日志运行骨架**

下面只规定职责和顺序，不是可直接复制的 Lua 代码。修复时用它判断代码错在哪一环，而不是重写。

```Plaintext
配置
  客户端控件容器索引 = 代码配置区中的既有值
  预期脚本短名称 = 代码配置区中的既有值，归一化为短名称
  锚定配置表 = 来自 8.2，含每个控件的锚点、中心点、相对尺寸与相对偏移

Runtime
  状态 = NEW
  主故障是否已输出 = false
  清理栈 = 空
  启动就绪尝试中 = false
  启动就绪已尝试次数 = 0
  启动就绪重试预算 = 根据目标环境真实启动观测配置的有限正整数
  最后一次未就绪原因 = 未开始

启动事务
  状态改为 STARTING
  先验证配置与锚定配置表；缺失或格式错误立即失败
  发布完整的重试状态与重入 guard
  启用只推进 STARTING 就绪检查的回调；此时不推进玩法

每次启动就绪尝试
  通过当前 API 文档声明的能力分别取得当前脚本实例、挂载容器和挂载查询结果
  任一运行时对象暂未就绪：记录 not_ready、次数和最后原因，本次尝试结束
  达到重试预算：只输出一个聚合故障
  对象全部就绪：核对运行时短名称一致、容器查询到的实例就是当前实例
  已就绪对象身份明确不符：立即失败，不继续重试
  创建玩法资源（按锚定配置表设置锚点、中心点、位置与尺寸）
  每次创建成功后立即登记对应清理动作
  状态改为 RUNNING
  通过当前文档声明的普通日志入口输出一次启动汇总

逐帧事务
  STARTING 时只推进一次启动就绪尝试
  仅在 RUNNING 时推进玩法
  整个事务共用一个错误边界

失败事务
  同一主故障只进入一次
  保存首个错误、阶段、状态和 traceback
  状态改为 FAILED
  停止输入、加载和逐帧逻辑
  按清理栈反向释放；清理错误只收集，不逐条打印
  生成一个带 BEGIN/END 的连续故障块
  通过当前文档声明的错误日志入口一次性输出

销毁事务
  重复调用不产生额外效果
  停止逐帧逻辑并反向执行剩余清理
  若清理失败且此前没有主故障，输出一个聚合故障块
  状态改为 DESTROYED
```

启动汇总和故障块至少包含：容器索引、预期脚本短名称、通过当前 API 取得的实际脚本名称、Runtime 状态、阶段、首个错误、traceback 和聚合后的清理错误。当前 API 文档没有提供某项运行时信息时写 `unknown`，不要虚构字段。

客户端控件容器索引只用于诊断标识，不能与动态控件运行时 ID 或来源模板 ID 比较。脚本挂载必须使用当前 API 文档声明的脚本上下文和容器查询能力独立核对。

**读骨架的方法**：把实际代码的每一环与上面逐行对照，找到第一处不一致的地方，那里通常就是故障所在。对照结果要写进报告的“直接原因”字段，而不是只说“某处写错了”。
