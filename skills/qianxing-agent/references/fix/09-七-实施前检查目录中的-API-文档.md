## 七、实施前检查目录中的 API 文档

每次开始排查、追加排查范围或修改代码前，严格执行以下步骤：

1. 先检查本 README 同级的当前 API 文档。它是本目录的首选当前 API 来源，用于查询接口声明、说明和限制；必须按本次故障涉及的能力定向检索，不能根据旧代码补全当前 API 文档没有写出的内容。

2. 记录实际使用的当前 API 文档路径和文件哈希，避免任务中途文件被替换后继续使用旧结论。如果当前 API 文档内部对同一接口存在实质冲突，把该项标记为 `unknown`，不要自行选择其中一个说法。

3. 只有同级的当前 API 文档缺失时，才从本 README 所在目录递归寻找名称或内容表明其为 API 文档、类型标注或接口声明的文件。不要把图片资产标注、示例脚本、本 README 或其他专题说明误认为当前 API 文档。

4. 创作者已经明确指出当前 API 文档时，以创作者指定文件为准。否则，递归搜索得到的多个候选若内容哈希相同，可视为同一份副本；若哈希不同且版本身份不明，列出候选路径请创作者确认。禁止自行按文件时间、目录名、文件大小或内容多少猜选，也禁止让旧副本覆盖同级当前文档。

5. 如果没有可确认的 API 文档，立即停止所有依赖编辑器 API 的探针、判断和代码修改，并直接向创作者索要当前 API 文档。禁止凭普通 Lua、Unity 经验、旧记忆、旧脚本、README、示例代码或最小探针反推缺失 API。

6. 文档存在时不要要求创作者重复粘贴。大型文档先用文件搜索和全文检索定位本次故障涉及的类型或概念，再读取命中定义的完整段落、相关类型、继承关系、重载、注释和限制；不要只看搜索命中的单行，也不要整份加载无关内容。

7. 判断“代码写错了”之前，按故障涉及的标识建立内部 API 核对清单。每个涉事能力都要确认：准确标识、所属对象、点号或冒号、参数顺序和类型、返回值数量和类型、字段读写性、枚举值、数值范围、回调参数与返回值、生命周期可用阶段、错误行为，以及对应的注销或销毁方式。多端适配使用的中心点、最小锚点与最大锚点字段必须出现在这份清单里。

8. 先查定义，再改代码。旧脚本中的标识只有在当前文档中重新找到并核对完整签名后才可判定为“用法正确”或“用法错误”；示例即使能运行，也不能证明其他参数、字段或隐含行为存在。

9. 文档没有明确说明的参数默认值、坐标语义、事件顺序、同步重入、资源来源或状态副作用都标记为 `unknown`。**不得把 ****`unknown`**** 当作故障根因的结论**；只能记为“证据不足”，并优先改用不依赖该未知项的方案，或向用户说明缺少的事实。

10. 最小探针只能验证当前 API 文档已经声明、但真实编辑器行为仍需确认的单个问题。探针只能调用文档已列出的能力，不承载玩法逻辑，不同时验证多个问题，得到结果后移除。它永远不能替代缺失文档，也不能创造文档中不存在的能力。

11. 修改完成后，从改动涉及的全部代码中提取编辑器 API 标识，逐项在当前文档中回查。核对实际调用形式、参数、返回值、字段读写性、枚举和清理入口；未找到依据的标识数量必须为零。语法层面的检查按 2\.5\.2 交给子 Agent，两者结论不得互相替代。

12. 如果任务过程中 API 文档路径、内容或哈希发生变化，废弃此前清单和审查结果，从第 1 步重新执行。不得把旧版本结论带入新版本。

只要准备根据名称、常见框架经验、旧代码、示例、数值范围或试运行结果补全一项文档没有写明的语义，就必须立即暂停当前判断并回到第 1 步定向检索当前 API 文档。尤其是把两个不同来源的数值放进同一个公式、范围判断、位置比较或状态判断前——包括把量测值与编辑器字段混用、把输入位置与布局位置混用——必须先在当前 API 文档中找到它们可以这样组合的明确依据。查不到时保留 `unknown`：能绕开就改用不依赖该关系的方案，不能绕开就停止对应实现并说明当前 API 文档缺少的事实，禁止先写猜测版本。

“最小探针”只处理一个已经被文档声明、但必须观察运行结果才能确定的问题，例如某项状态切换后是否保留先前写入值。没有可运行环境或仍需用户补充事实时，保持 `unknown` 或 `pending`，不得把推测写成验证结果，也不得为了继续推进而先改一版试探。
