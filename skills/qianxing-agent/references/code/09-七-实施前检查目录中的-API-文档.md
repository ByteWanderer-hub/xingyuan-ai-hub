## 七、实施前检查目录中的 API 文档

每次开始新需求、追加需求或需求变更时，严格执行以下步骤：

1. 先检查本 README 同级的当前 API 文档。它是本目录的首选当前 API 来源，用于查询接口声明、说明和限制；必须按本次功能定向检索，不能根据旧代码补全当前 API 文档没有写出的内容。

2. 记录实际使用的当前 API 文档路径和文件哈希，避免任务中途文件被替换后继续使用旧结论。如果当前 API 文档内部对同一接口存在实质冲突，把该项标记为 `unknown`，不要自行选择其中一个说法。

3. 只有同级的当前 API 文档缺失时，才从本 README 所在目录递归寻找名称或内容表明其为 API 文档、类型标注或接口声明的文件。不要把图片资产标注、示例脚本、本 README 或其他专题说明误认为当前 API 文档。

4. 创作者已经明确指出当前 API 文档时，以创作者指定文件为准。否则，递归搜索得到的多个候选若内容哈希相同，可视为同一份副本；若哈希不同且版本身份不明，列出候选路径请创作者确认。禁止自行按文件时间、目录名、文件大小或内容多少猜选，也禁止让旧副本覆盖同级当前文档。

5. 如果没有可确认的 API 文档，立即停止所有依赖编辑器 API 的设计、探针和代码实施，并直接向创作者索要当前 API 文档。禁止凭普通 Lua、Unity 经验、旧记忆、旧脚本、README、示例代码或最小探针反推缺失 API。

6. 文档存在时不要要求创作者重复粘贴。大型文档先用文件搜索和全文检索定位本次功能涉及的类型或概念，再读取命中定义的完整段落、相关类型、继承关系、重载、注释和限制；不要只看搜索命中的单行，也不要整份加载无关内容。

7. 写代码前，按功能建立内部 API 核对清单。每个将要使用的能力都要确认：准确标识、所属对象、点号或冒号、参数顺序和类型、返回值数量和类型、字段读写性、枚举值、数值范围、回调参数与返回值、生命周期可用阶段、错误行为，以及对应的注销或销毁方式。多端适配使用的中心点、最小锚点与最大锚点字段必须出现在这份清单里。

8. 先查定义，再写代码。旧脚本中的标识只有在当前文档中重新找到并核对完整签名后才可复用；示例即使能运行，也不能证明其他参数、字段或隐含行为存在。

9. 文档没有明确说明的参数默认值、坐标语义、事件顺序、同步重入、资源来源或状态副作用都标记为 `unknown`。优先改用不依赖该未知项的实现；无法绕开时再向创作者说明缺少的事实。

10. 最小探针只能验证当前 API 文档已经声明、但真实编辑器行为仍需确认的单个问题。探针只能调用文档已列出的能力，不承载玩法逻辑，不同时验证多个问题，得到结果后移除。它永远不能替代缺失文档，也不能创造文档中不存在的能力。

11. 完成代码后，从代码中提取全部编辑器 API 标识，逐项在当前文档中回查。核对实际调用形式、参数、返回值、字段读写性、枚举和清理入口；未找到依据的标识数量必须为零。语法层面的检查按 2\.5\.2 交给子 Agent，两者结论不得互相替代。

12. 如果任务过程中 API 文档路径、内容或哈希发生变化，废弃此前清单和代码审查结果，从第 1 步重新执行。不得把旧版本结论带入新版本。

只要实现准备根据名称、常见框架经验、旧代码、示例、数值范围或试运行结果补全一项文档没有写明的语义，就必须立即暂停当前设计并回到第 1 步定向检索当前 API 文档。尤其是把两个不同来源的数值放进同一个公式、范围判断、位置比较或状态判断前——包括把 HTML Demo 的量测值与编辑器字段混用——必须先在当前 API 文档中找到它们可以这样组合的明确依据。查不到时保留 `unknown`：能绕开就改用不依赖该关系的方案，不能绕开就停止对应实现并说明当前 API 文档缺少的事实，禁止先写猜测版本。

“最小探针”只处理一个已经被文档声明、但必须观察运行结果才能确定的问题，例如某项状态切换后是否保留先前写入值。没有可运行环境或仍需创作者补充事实时，保持 `unknown` 或 `pending`，不得把推测写成验证结果。

### **7\.1 涉及图片时按实际需求获取图片资产 ID**

只有当前实现步骤确实需要用图片资源填充图片控件时，才执行本节。不要在容器/脚本入口交接阶段提前索取，也不要把 `image_sample`、`Image_sample_by_id.json` 或其他图片资产数据标注文件列为默认必需项，更不要要求创作者提供它们。

本节给出唯一一条图片资产获取流程，共四步；任何其他位置的图片流程说明都以本节为准。

```Plaintext
第 1 步  列清单
  把当前步骤实际需要显示的图片按语义列清楚，例如“小鸟”“猪”“弹弓”；
  同时列出本次任务所需的所有图片类型（按钮背景、图标、装饰边框等）。

第 2 步  由子 Agent 检索候选
  按 2.5.1 启动图片资产查找子 Agent，用图片资产数据标注在素材库中查找匹配项；
  主 Agent 不亲自做大范围检索，也不把标注原文读进主上下文。

第 3 步  主动告知并请用户确认
  拿到候选后必须主动告知用户：找到的图片是什么、计划用在哪个控件或场景中，
  并请用户判断是否适用（例如“我找到图片 ID xxx，计划用作主按钮背景，是否合适？”）。
  用户确认前不得写入正式代码。

第 4 步  仍然找不到时才求助用户
  若整类都没有合适候选，或候选被用户否决，则向用户请求帮助；
  此时需把图片需求（尺寸、风格、内容描述）和用途详细列出，以表格形式清晰呈现。
  中文用户按下面的编号格式，非中文用户用用户语言表达相同内容。
```

> 我现在需要用一些图片资产来实现对应需求，请按照表格顺序，依次向我提供下列图片资产的ID：

|类型|关键词|风格|内容描述|用途|
|---|---|---|---|---|
||||||

补充约束：

1. 图片来源类别、资产 ID 的实际类型以及绑定时需要的其他参数，必须从当前 API 文档和创作者提供的资源记录核对。禁止让创作者猜枚举；文档或资源记录没有说明时标记为 `unknown`，不得默认填入 README 中曾经出现过的值。

2. 创作者直接提供图片资产 ID 时一律接受，不必经过子 Agent 检索。允许创作者提供纯 ID、带名称的 ID、资源记录或包含 ID 的路径/文件，AI 自行提取其中的有效资产 ID，不得因回复格式不同要求重发。

3. 不得把图片控件模板索引、动态控件运行时 ID 或实例的来源模板 ID 当成图片资产 ID。多个实际图片需求可用一个编号列表一次性索取。

4. 对每个实际使用的资源至少记录：当前文档要求的来源信息、资产 ID、语义/形状、证据来源和证据状态。相同 ID 的资料互相冲突时标记为 `unknown` 并停止使用，禁止按文件时间、ID 范围、类别或印象猜选。

5. 子 Agent 返回的候选只作为线索，一律先记为 `provided_unverified`；即使主 Agent 核对完成，用户确认也只代表“这个素材被采纳”。资源类型与来源只有在当前 API 文档明确支持时才可记为 `documented`，否则保持 `provided_unverified` 并写清真机状态为 `pending`。

6. 图片资产 ID 或数据标注只能证明资源选择，不能证明真机成功绑定。仍须按 9\.4 对实际图片控件做首次绑定、文档支持的状态核对，并按 10\.1 第 4 项完成可见结果验证。
