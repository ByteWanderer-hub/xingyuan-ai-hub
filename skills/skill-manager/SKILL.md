# 技能维护

1. 读取仓库 AGENTS、目录、当前版本及已有同主题记录。技能真源位于 skills；安装副本不得手工修改。
2. 通读本次涉及的入口和参考。区分完全重复、摘要与展开、跨平台差异、同编号不同含义；只有有内容覆盖证据才能删除重复正文。
3. 将完整正文保留在一个位置；旧路径留兼容跳转，更新引用与“权威版本”声明。保留专有规则、来源许可证、历史证据与不可替代资产；有冲突时明确当前权威并记录待核实项，不用猜测折中。
4. 新技能先核对来源/许可证、脚本和权限；不因引入执行第三方安装或扩大业务授权。每次新增或修改都按 [入口联动维护](../xingyuan-router/SKILL.md#技能变更必须同步维护入口) 核对 routes.json、选择规则、平台与缺口；更名/合并/删除同步清理旧路由。与技能同提交上传，安装副本同时更新入口。路由无变化时记录核对结果。
5. 归类每条索引：能直接执行并验收的填 `kind: skill`；只给原则、数值、判据、案例的填 `kind: experience`，且不得带脚本或冒充实现；本机工具清单类填 `kind: external`。依赖库外 MCP、网关或平台时，在 `externals[]` 登记（kind/status/purpose/note/keywords）并在该技能 `requires` 里引用，不把库外能力写成库内技能。
6. 验证名称、链接、关键词正反例、缺失技能提示、`kind` 分类、`externals` 状态、安装后的相对路径。记录实际范围、证据和未验证项，再按用户授权提交到仓库。

查找或调用已有技能用 xingyuan-router；当前技能只负责维护。源码完整、客户端发现、插件可用和真机通过分别报告。

## 从项目经验优化技能

用户要求复盘并优化技能时，先从当前对话和允许读取的同主题证据提炼，不因“完整总结”全仓扫描、启动业务恢复或修改游戏。先区分用户明确决定、重复出现的问题、已证实原因、推测和仍未验收的实现；聊天中曾称“完成”不是所有验证都通过的证据。

- 把经验写成“触发场景 → 原因/不变量 → 做法 → 反例/验证边界”，归入职责最接近的现有技能；复杂内容放按需参考，入口只给路由。不为单个项目再建一套重复的技能或总规则。
- 项目专属配方、关卡编号、颜色、节奏和权限不升级为跨项目铁律。值得保留的案例注明来源和适用条件；未验证方案只能作为风险/待测方法，不能宣传为成功范式。不要发布本地地图 ID、用户素材路径、凭据或完整私有交接。
- 复盘既记录设计，也覆盖预览到原生的落差、用户保存参数、状态/取消、真实输入、验收证据和交付边界。重复返工优先补可执行检查，不堆泛泛的“更加注意”。
- 检查旧文是否与新结论矛盾，修正实际冲突并保留必要来源；同一全文只由一个技能持有，其他入口链接。既有授权与用户新决定优先，技能维护不擅自改变业务权限。
- 验证新指导能处理原失败场景，也不会误触发普通业务请求；按既有同步授权完成真源、远端核实和实际使用副本更新。只改文档时不为验证技能而重新部署游戏。
