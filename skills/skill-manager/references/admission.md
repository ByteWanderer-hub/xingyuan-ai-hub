# 新技能录用守则

适用范围：新增/导入技能、把项目经验沉淀为技能、把外部工具或 MCP 接进本库索引、优化已有技能的分类。
目标：**在写索引之前**把「技能 / 经验 / 外部 MCP 与服务」分清，避免三类混写，也避免把库外能力写成库内技能。

## 一、先判类别（顺序不可颠倒）

| 顺序 | 判据 | 结论 | 写入位置 |
| --- | --- | --- | --- |
| 1 | 需要库外 MCP、网关、平台或软件才能生效，本库只能提供对接说明？ | 外部依赖 | `routes.json` 的 `externals[]`，依赖它的技能在 `requires` 引用 |
| 2 | 有可执行步骤或脚本，且产出可核对（文件、控件、消息、报告、测量结果）？ | 技能 | `skills[]`，`kind: skill` |
| 3 | 只给原则、数值、判据、案例、审视清单，本身不产出实现？ | 经验 | `skills[]`，`kind: experience`，**不得带脚本** |
| 4 | 只是本机工具清单与状态核对？ | 外部工具清单 | `skills[]`，`kind: external` |
| — | 以上都不是：与现有技能重复、无法验证、许可证不明 | 不录用 | 只在 handoff 记录，不写索引 |

判定只看证据，不看名字：

- frontmatter 的 description 自述（“只提供原则”“NOT for coding”“第三方参考”是经验信号）；
- `references/` 里是判据/数值还是操作步骤；
- 目录里有没有 `.py` / `.ps1` / `.js` / `.lua`（有脚本不等于自动算技能，脚本必须支撑可验收产物）；
- 是否必须调用外部服务（必须调用的部分是 `externals`，不是技能）。

拿不准时按「能不能直接执行并验收」二选一；**宁可判经验，也不要把原则包装成技能**。

## 二、准入硬门槛（缺一项就不写索引）

1. **来源**：URL + 固定 commit 或版本；原样收录与改写分别写进 `NOTICE.md` / `UPSTREAM.md`。
2. **许可**：明确可再分发。`NOASSERTION`、来源不明、需付费/订阅的，不录用。
3. **安全**：不夹带凭据、Cookie、私人聊天全文、本机绝对路径、地图 ID；第三方脚本先人工审查，不执行未知安装脚本。
4. **结构**：目录名 = frontmatter `name`；`SKILL.md` 的 name/description 完整；相对引用可达。
5. **去重**：与现有技能职责重叠时先合并或链接，不开第二份正文（同一全文只由一个技能持有）。

## 三、写索引的顺序

1. 目录与正文（先落文件）。
2. `routes.json`：`name`、`kind`、`purpose`、`platform`、关键词；技能类补 `requires`。
3. 外部依赖：`externals[]` 加 `name`/`display`/`kind`(mcp|service|platform|software)/`status`(ready|unverified|missing)/`purpose`/`note`/`keywords`，并在依赖它的技能 `requires` 里引用。
4. `skills/xingyuan-router/SKILL.md`：快速表加行（经验标（经验）、工具清单标（外部））、三类入口表更新计数、必要时改细分入口与缺口。
5. 测试：新增正例（说得出类别）与反例（不该命中、不该被判成技能）。
6. 提交推送 → 同步使用副本 → 记录客户端发现状态。

## 四、常见误判与改判

| 误判 | 为什么错 | 改判 |
| --- | --- | --- |
| 有脚本就一律算技能 | 脚本可能只是素材生成或一次性脚本，不构成可执行流程与验收 | 看是否能产出可核对结果；否则降为经验或删脚本 |
| 只有一个 GitHub 项目 README 就建技能 | 没有本地可验证流程，等于把外部项目抄成本库能力 | 登记 `externals`，正文只写接入边界 |
| 把 MCP/网关写成技能 | 技能会被当作“已有能力”加载，实际调不通 | 进 `externals[]` + `requires`，状态如实写 missing/unverified |
| 把原则写成“技能”并承诺效果 | 无脚本、无验收，容易被当成实现 | `kind: experience`，写明落地要配哪个平台技能 |
| 同一主题再建一份技能 | 两份正文会分叉 | 合并进现有技能，旧路径留跳转 |
| 关键词直接抄技能名 | 用户说法与技能名不一致，召回低 | 加用户自然表达正例、易误触发反例 |

## 五、库外依赖缺失时的处理

`externals[]` 里 `status: missing` 的条目不是“已具备能力”，处理顺序固定，不许跳步：

1. **先核验**：命令是否在 PATH（`Get-Command` / `which`）、MCP 是否在 profile 配置里，不凭“应该装过”判断。
2. **缺失就提示安装**：给来源（仓库/官方文档）、许可、运行前置（Node、工具链、本地服务端口），一次说清，然后等用户决定。
3. **用户不安装、或装完仍不可用 → 本次不使用该能力**：不假装执行、不拿相邻技能冒充（例如用 `systematic-debugging` 冒充逆向）、不把未发生的结果写进技能正文或交接记录当成已完成。
4. **装好并实测后**才把 `status` 改为 `ready`，同时更新 note 与 handoff；只改状态、没实测的不算。

同一套顺序适用于任何库外服务（MCP、网关、编辑器、外部软件）。

## 六、完成定义（缺一项不算录用完成）

- 索引里 `kind` 明确；`experience` 无脚本；`externals` 有状态且被 `requires` 正确引用。
- 路由能命中该条，且反例不误触发；全量测试通过。
- handoff 记录来源、类别判定依据、验证结果、未验证项。
- 真源已提交推送，使用副本已同步；客户端实际发现与真机验收单独记录，不合并成“已通过”。
