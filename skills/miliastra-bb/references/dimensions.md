# 多维度体感体检（D1–D6）

> 用途：**miliastra-bb 步骤 3** 的作业手册。步骤 2 查**工程**（有没有、能不能做），这一步查**人**——玩家碰到这个角度 / 这一版，会是什么感觉。
> 一句话原则：**把"我觉得没问题"翻译成"玩家第 N 次碰到时会怎样"**；每个结论都得像是能拿去验证的（带数字、带反例），而不是口气。
> 加载时机：需要深入体验评审时只读相关维度；澄清与推进遵循 [技能入口](../SKILL.md)，不要求固定提问格式或轮数。
> 边界：本文件只管**需求阶段的体感预判与风险标记**。视觉/版面怎么改 → `miliastra-ui`；性能怎么优化、代码怎么写 → `miliastra-code` / `lua-eggy-code`。

---

## 0. 怎么用

按本次改动选择相关维度；只有用户要求全面评审或复杂玩法确实需要全局权衡时才用六维矩阵。不适用项可省略，使用完整矩阵时写明 N/A 理由。
结论说明观察指标、来源、反例及应对；预测不是实测，不编造数字填表。涉及改变用户规则或接受重大体验风险时给出影响和选项，已有明确决定不重复询问。
下面的问法和模板用于辅助判断，可按任务裁剪；文中的“步骤 3/6”等沿用旧编号，不规定执行顺序。选择实际影响取舍的维度，不要求每个方案凑齐固定数量。

## D1 玩家体感 —— 他第一次碰到会怎么理解、怎么反应

**为什么算一维**：一个机制"逻辑正确"和"玩家能懂"是两件事；上手期的困惑是**静默流失**的最大来源。

**核心问句（挑着问，别硬套）**：
1. 玩家第一次碰到**具体会做什么动作**？他以为会发生什么？
2. 前 5 秒他**看到/听到什么**？能不能自己得出"我该干什么"？
3. 没人教、没有教学关，**他能自己搞明白吗**？要靠几层提示？
4. 操作有反馈吗——视觉 / 听觉 / 数字 / 抖动 / 文字？
5. 这个角度（视角·位置·朝向）下他**看得见关键信息吗**？（"碰到这个角度"的字面意思：视线、站位、朝向）
6. 误触会怎样？代价大不大？

**量化套路**（单位要具体）：
- 认知时间：首次接触 → 理解玩法 秒数；
- 反馈延迟：输入 → 反馈 毫秒 / 帧数；
- 反馈通道数：视觉 / 听觉 / 数字 / 抖动（列出来）；
- 需要文字说明的机制数（**"要说明书"的机制数量是个警报指标**，理想 0）。

**产物模板**：
```
D1 玩家体感：首次接触时玩家动作=<…>，预期理解=<…>，<N> 秒内能懂；
  反馈=<延迟 + 通道（视觉/听觉/数字）>；
  正例：<同类游戏的对照写法>；
  反例：<最容易出现的误解> → 破法：<具体手段>
```

**典型翻车**：提示没有 / 只有文字提示 / 手感延迟 >100ms / 需要读说明书 / 关键信息被视角挡住或出画（"这个角度根本看不见"）。

## D2 失败与重复 —— 第 1 次 / 第 10 次 / 第 50 次分别什么感觉

**为什么算一维**：UGC 图的寿命几乎全在"重复"上；一次失误就全盘重来的设计，最好玩的一局也留不住人。

**核心问句**：
1. 第一次失败，玩家**学到东西了吗**？（看得到自己错在哪吗）
2. 连输 3 次会**想再来一次还是想骂人**？
3. 第 50 次重复同一段——**会腻吗**？有变化、有捷径、能跳过吗？
4. 惩罚有数字吗（复活秒数 / 掉多少资源 / 掉多少分）？**有上限吗**？
5. 死亡/失败到重开要几步、多少秒？
6. 有没有"新手保护 / 难度自适应 / 人机陪跑"这类缓冲？

**量化套路**：首次失败认知时长（秒）/ 连续失败容忍次数（N 次）/ 重复段落长度（秒）/ 重开步数与秒数 / 惩罚数值与上限 / 可跳过性与变化手段（列出）。

**产物模板**：
```
D2 失败与重复：第 1 次=<学到什么>，第 10 次=<感觉>，第 50 次=<感觉 + 防腻手段>；
  惩罚=<数字 + 上限>；重开=<步数/秒数>；
  正例：<…>；反例：<…> → 破法：<…>
```

**典型翻车**：无反馈的失败（不知道错哪）；惩罚无上限且累加；重复段落长且不可跳过；难度只有一条线性曲线（前 3 分钟就劝退）；死亡无逃生通道（卡死/掉出地图）= D6 联动。

## D3 公平与社交 —— 联机 4/8 人公平吗

**核心问句**：网快/网慢的差多少？有人挂机、掉线、中途退出会怎样？**所有人同时做同一动作会怎样**（抢、堵、卡位）？能不能互相破坏体验（恶意道具、霸占资源）？人数不足 4 人时玩法还成立吗？

**量化套路**：最小/最大人数；人数不足时的补偿；一个人卡住时其他人的等待秒数；每人可占资源的数量/比例；掉线后的处理（保留成绩？补人？）。

**产物模板**：
```
D3 公平与社交：人数=<min/max>；对等性=<…>；
  挂机/掉线处理=<…>；互相破坏的风险=<…>；
  正例：<…>；反例：<…> → 破法：<…>
```

**典型翻车**：一人卡住全员等 / 道具能恶意堵路 / 人数不对称明显吃亏 / 必须熟人局才玩得起来。

---

## D4 平台规则与合规 —— 过审吗、素材干净吗

**核心问句**：涉不涉暴力血腥/恐怖？涉不涉付费或诱导付费？用的素材有商用许可吗（官方素材库 / 自己画 / 网友图）？内容分级与未成年保护？玩家名/自定义文本的敏感词过滤？平台对 UGC 内容有自己的公示与审核规则，命中的要写清楚。

**量化套路**：命中风险条数；每条给处置（换素材 / 加过滤 / 调表现强度）；拿不准就 `[待确认]` + 查证路径（平台适配文件 §能力层 / 官方文档 / 平台规则页）。

**产物模板**：
```
D4 平台规则：风险项=<逐条 + 处置>；查不到依据的=<[待确认] + 补证路径>
```

> **红旗清单**（命中任一条就必须查，不许"应该没事"）：血腥/恐怖元素、真人照片或他人作品、第三方 IP 形象与音乐、诱导付费或抽奖、涉赌转盘、玩家可自定义公开文本、未成年人可接触的强对抗。

## D5 性能与规模 —— 元素翻倍还成立吗

**核心问句**：同屏元素/控件/实体各几个（**给数字**）？帧率稳不稳？低配机（手机）呢？联机人数翻倍（4→8）会怎样？每帧要做多少次计算/遍历（循环建控件、定时器频率）？极端情况（全屏特效、所有人同时触发）呢？

**量化套路**：同屏对象数 + 刷新频率 + 单帧开销量级；规模翻倍时的降载方案与上限值。**拿不到实测就写** `[待确认] + 补证办法`（真机试玩 N 局 → 用平台日志工具读耗时/帧率，见平台适配文件）。

**产物模板**：
```
D5 性能与规模：同屏=<N 个 / 频率>；上限=<判定依据：实测 or [待确认]+补证办法>；
  翻倍方案=<降载/分批/池化>；正例：<…>；反例：<…> → 破法：<…>
```

**典型翻车**：PC 上流畅、手机端崩；人数一满就掉帧（而掉帧直接打崩 D1 手感）；循环里每帧建控件；元素"上不封顶"。

## D6 可撤性与维护 —— 上线后怎么收、三个月后还看得懂吗

**核心问句**：这个改动有什么副作用？出问题能一键关掉吗？卡死/掉出地图有自动判负或逃生通道吗？玩家骂了怎么回滚（改哪个数？）？作者三个月后再看这版还认得吗？改一处会不会崩三处（牵连面）？

**量化套路**：开关（有/无、键名）；回滚动作（几步）；牵连点（文件数 / 函数数 / 配置项数）；卡死自动判负阈值（秒数）。

**产物模板**：
```
D6 可撤性与维护：回滚=<动作 + 步数>；开关=<键名 or 无>；
  牵连=<文件/函数数>；卡死兜底=<阈值秒数>；
  正例：<…>；反例：<…> → 破法：<…>
```

**典型翻车**：卡死无逃生通道；改一个数要动三处；没有开关只能整图换版本；参数散落在多个文件里。

## 1. 输出形状：「维度 × FP」矩阵

复杂需求需要持续记录时，将相关结论写入既有清单；完整评审可采用下表，小任务不强制矩阵：

| FP | D1 玩家体感 | D2 失败与重复 | D3 公平与社交 | D4 平台规则 | D5 性能与规模 | D6 可撤性与维护 |
|---|---|---|---|---|---|---|
| FP1 机关即死 | 首次 0.5s 内看到警示；1.5s 内懂规则；反馈=红色闪烁+音效 | 第 1 次懂、第 10 次可跳过、第 50 次有 3 条路线变化；惩罚=回checkpoint，上限 1 次 | N/A：单人图 | 无血腥，用官方素材 ✅ | 同屏 12 个，60fps 达标；翻倍=分批激活 | 回滚=改 1 个阈值；牵连 1 个文件 |
| FP2 排行榜 | <…> | <…> | <…> | <…> | <…> | <…> |

**格子写法**：数字优先；N/A 写理由；`[待确认]` 写补证办法。**这一列一列看下来，能看出"哪个 FP 在体验上最脆"**。

## 2. 从体检结论到决策（步骤 6/7 怎么用）

| 体检结论 | 处置 | 传导 |
|---|---|---|
| 某维风险高、用户还没拍板 | 将影响玩法或验收的未定决策集中询问，给出证据、选项和代价 | 写进「待确认列表」 |
| 命中 D4 合规红旗 | **先查证再谈实现**，不许"先做再说" | 不查清不进交接 |
| D2/D5 缺最坏情况预案 | 明确责任与兜底（谁测、什么标准算崩） | 写进「撤销条件」 |
| 玩家体验代价大但用户要保留原口径 | **尊重原玩法**（R0），如实记风险 + 写谁接受了它 | 写进「未做/Out of scope」或「复测记录」 |
| 某维说不清（信息不足） | 标 `[待确认] + 补证办法`，别编 | 列进「待确认列表」 |

> **不要**把维度当"评分卡"打分论总评——每维是**独立探针**，命中问题就足够（一维的问题不会被另外五维的高分抵消）。

## 3. 数字从哪来（不许编）

| 类型 | 合法来源 |
|---|---|
| 平台硬边界（人数上限、帧率口径） | 平台适配文件 §能力层 + 官方文档；查不到 → `[待确认]` |
| 手感/节奏类数字（反馈延迟、认知时间） | 同类玩法实测 + `web_search` 对照 + 本机真机试玩（用平台日志工具取证） |
| 惩罚/难度数值 | 同类公式 + 本项目既有配表；都没有 → 标"待实测"，给测法 |

**禁止**：把"经验感觉"写成数字（"大概 0.2 秒吧"）；把没测过的帧率写成事实；把官方文档没写的能力当存在。

## 4. 常见错误

| ❌ | ✅ |
|---|---|
| 相关维度只写"体验不错" | 给出可观察指标、依据、反例与应对；不为凑齐数字编造证据 |
| 只回答"会不会好玩" | 根据实际玩法评估首次体验、重复、联机或规模变化，不套用无关人数与次数 |
| 完整矩阵中不适用的维度留空 | 显式 `N/A：<理由>`；局部评审可省略无关维度 |
| 编数字充证据 | 给来源，拿不到就 `[待确认] + 补证办法` |
| 把体验当**口味**争论 | 把体验当**假设**验证（给数字和反例，能拿去测） |
| 体检发现玩法有风险就自己改口径 | **R0**：先问用户；用户坚持就如实记风险 |
| 需要后续实施却没有传递体验结论 | 在既有任务记录或交接中写清相关结论；小任务可在回复中交付 |
