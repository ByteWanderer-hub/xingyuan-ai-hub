## 需求原文（R 编号）
- R1：到零食位置没有特效和提示也没加分
- R2：老师砖头没有粉笔飞过来（「砖头」=「转头」笔误，场景对读确认）
- R3：公告牌上分数一直是0
- R4：那开始完善项目吧

## 教训一：三条 bug 是一个系统性问题的三个影子——先取证再拆分
取证（诊断试玩 + 日志 tail）把 R1「没加分」**证伪**了：`[snack] EAT #2 +10 score=20` 多次——加分代码是通的。真相链：
1. 吃零食**零反馈**（无特效/无提示/模型不消失）→ 玩家不知道加了分；
2. 老师转头 0.6s 后隐形 -20（场景里根本没有粉笔实体，飞行代码静默跳过）→ 分被秒清零；
3. 手机 +5/s 结构性死区（`classActive` 要求人在左教室，凳子全在右教室，永不同真）；
4. 【未报告，主动上报】猜拳负数取模恒平局 + 胜负映射颠倒 → 右牌永远 0:0、+30 永远拿不到。

> **方法沉淀**：玩家的 bug 报告是「现象+归因猜测」。先跑一局带 print 的试玩翻日志，把「现象」和「机制」分开——R1 的机制是好的，坏的是反馈层；不取证就会去「修计分」反而把对的东西改坏。

## 教训二：bug 单里夹着需求（六问判定器的实战拆分）
| 用户原话 | 拆出 | 组 |
|---|---|---|
| 「没有特效和提示」 | 吃零食即时反馈 | **A组**（代码里根本不存在） |
| 「没加分」 | 计分机制 | 证伪：B组无需修（是反馈+隐形惩罚的感知问题） |
| 「没有粉笔飞过来」 | 粉笔实体缺失 | **A组**（飞行代码就绪但场景无此组件——补组件/替身） |
| 「分数一直是0」 | 手机死区 + 猜拳判定 | **A组**（前者规则语义矛盾、后者判定双 bug） |

「没加分」若按字面去修计分，就是**把对的改坏**——这是本案例最有传授价值的一笔。

## 教训三：方案对话要给「量化后果」，偏离推荐项也要确认
- 手机得分给了三选项，用户选「坐凳无条件 +5」（非推荐项）→ 追加一轮确认量化后果（200÷5=40 秒坐赢）→ 用户接受 → 拍板有效。
- 规则 B（不在座位就罚）落地时发现与既有需求冲突（全图判罚会让猜拳站圈挨炸、+30 拿不到）→ 不擅自取舍，实现为「判罚区全图 + 站圈豁免」并向用户披露限定理由。

## 教训四：口径在实测中收紧是常态，回填要跟上
- 「在椅子上=安全」最初实现为「凳子 1.2m 内」，用户实测反馈「站凳子边没烟花」→ 收紧为「**点了坐下**才算」；
- 「教室」最初沿用 v3.1 的西屋判定框（x<-9.5），用户站凳子区（框外）永不受罚 → 改「全图一整间」；
- 老师朝向 ±x 写反了 9 个版本没被发现——**零反馈的玩法会掩盖一切视觉 bug**；反馈本身是探测器。

## 交接与迭代节奏
