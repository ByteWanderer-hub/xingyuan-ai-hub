# 需求分析方法

这是 [技能入口](../SKILL.md) 的可选分析工具，不是固定七步流程。按当前歧义或风险选用；完成已授权任务所需的分析后继续推进。

## 多项需求的追溯

复杂规则可将原文编号为 R、可交付功能编号为 FP，记录需求 → 实现范围 → 验收的对应关系。保留关键原话，查漏项和无授权扩项；小任务不强制编号或矩阵。
替代路线若使某项要求失去意义，应点明改变及影响，由用户决定，不能把没有实现的要求记成已满足。

## 现状与能力

根据任务检查相关逻辑、触发配置、场景资源和 API，记录已存在、部分存在、需新增、已证实不支持或未知。证据可为源码位置、配置项、资产 ID、文档或实测。没有找到接口只能说明未查到；无现场通道时写出待核实项。

## 修复与新增

判断用户是否要恢复既定行为，还是改变预期/增加能力。例如“修复计分不对”与“改为按时间加权计分”不同；“修复按钮失效，顺便加排行榜”包含两项。实现需要增字段或组件不自动改变用户请求的性质，但需评估数据、兼容和授权影响。

## 体验与方案

选取会改变本次决策的维度，用可观察行为、合理目标和反例说明取舍。数字注明来源，估算明确标为估算；不编造帧率、操作延迟或过审结论。
存在实质方案分歧时给出少量可行选项和代价。问题尽量集中，复用用户已给的答案；不为凑轮次追问文件位置等可自行获取的信息。

## 玩法复刻

原型机制不确定且影响实现时查可靠来源。若原作与用户描述不同，说明差异及对输入、碰撞、层级等的影响，由用户选择忠于原作还是自己的改版；不预设原作优先。
参考 [双相案例](examples/yuan-biphase-flip.md) 或 [俄罗斯方块案例](examples/yuan-tetris-first-game.md) 时，案例仅提供经验，不自动继承其全部流程和权限。

## UGC 规范文档对齐

仅在用户要求以项目核对 UGC 规范或评审文档时使用。按指定范围对照条款和项目证据，区分一致、需适配、冲突、未知；说明遗漏、贡献及重新评估条件。
标注文档时保留原稿，沿用用户指定的审阅格式。需要使用 `scripts/mark_docx.py` 时先核实本机运行条件，不依据历史环境断言 Python 不可用。普通软件文档审阅不触发本技能。

## 记录与交接

复杂任务可用 [边界清单模板](templates/boundary-list-template.md)，保留适用字段。待定决定、可继续部分、验收与权限必须清楚；不将待定项默认为批准，也不让无关待定项阻塞独立工作。
