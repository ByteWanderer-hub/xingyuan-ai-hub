# UGC 需求边界

产出可执行的范围、验收标准和待定决策。范围已明确时直接转入对应实现技能，不把分析流程变成开工审批。

## 判断与推进

- 保留用户的规则、胜负判定、数值和摆位；不以优化、平台限制或原作玩法为由擅自改写。替代路线改变用户体验或验收时，明确受影响要求并让用户决定。
- 复用已经确认的目标、方案和授权。只有影响玩法、范围、权限或验收的缺项需要集中澄清；普通实现选择和可独立解决的技术问题自行推进。无固定提问轮数、逐工单再授权或每功能点多方案要求。
- 事实与用户描述、设计预期或其他证据存在实质冲突时，提供证据、影响与可行选项；不把“可能有问题”写成“没问题”。不影响方向的工具错误先定位、修复，不自动升级成产品决策。
- 将恢复既定行为的修复与新增玩法分清，混合请求分别记录；是否需要新组件或修改数据结构用于评估影响，不单凭文件数或实现手段判定为新增需求。
- 仅核对涉及的逻辑、配置、场景和平台能力。结论标明来源；查不到 API 是 `unknown`，不等于已证明不支持。工具不可用不编造现状。
- 模糊体验词转为可观察验收标准；预判与实测分开。只评估与本任务相关的玩家体验、重复失败、公平社交、平台规则、性能规模、可撤性风险。

## 实施与交接

- 只请求分析时交付分析结果；用户已要求实现时，在范围明确后继续完成实现、必要验证与返修，不停在清单或“已派工”。已授权事项无需逐项再确认。
- 涉及新增脚本、容器层级或数据契约的复杂改动，先厘清相关结构与编辑器分工；复用已有架构，不要求每项任务重新完整规划。
- 交接说明目标、范围、已知现状及证据、验收、允许写入位置、权限和未验证项；同一文件只有一个执行者。技能分工不自动要求启动其他代理。
- 存档结构、排行榜、商业化或用户手工配置发生变更时，核对现有授权是否覆盖具体影响；未覆盖再询问。
- 无法交互时可完成分析和独立工作，列出待决策项；假设不构成修改玩法或外部写入的授权。
- 小任务在当前回复或既有记录交付即可；仅在任务需要持续追踪时使用文档。不得因本技能自动 git 提交、推送、发布或新建一套文档。
