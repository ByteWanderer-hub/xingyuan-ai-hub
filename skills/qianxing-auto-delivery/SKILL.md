# 千星自动交付

主聊天负责调度，将 Astra 的大纲交给 Sol，并把 Sol 通过验收的最终成果转交用户。

## 原则与边界

- **质量优先于节省。** 先满足效果、正确性、完成度和必要验证，再节省额度、时间及协调成本。不用明显不足的方案换取省额，也不把更多代理、更贵模型或重复检查当作质量本身。
- 遵守当前工作区 AGENTS；在共享技能仓库按根规则定位 `handoffs/active/` 的已有主题。千星业务阶段先确认目标游戏工程，再按其规则读取 `instructions/qianxing/AGENTS.md`（实际存在或已配置时）及所指技能，不把共享仓库当作游戏工程。只讨论、审查或维护规则时，仅做对应部分，不启动业务恢复。
- 用户明确的分工、模型和权限优先。自主分工不扩大任务、素材处理或发布部署授权；不改全局默认模型，不搭建额外 API 服务，不创建用户侧新聊天、持久 Goal 或定时任务。

## 启动与续做

- 拟定方案、派工或建文档前，按工作区规则定向定位同名交接及同主题已有文档，核对对象、当前状态和未完成项，沿用唯一主题入口。纯技能维护只读相关规范，不读取业务交接或启动业务恢复。
- 新文件或新一轮反馈先与已确认范围比对，只处理新增、变化和仍未解决项。遵守指定工作表/资料边界；截图标注要实际查看并关联到具体对象。表中“已完成”、旧截图和口述状态分别作为来源记录，不能代替当前版本证据。新具体反馈可重新打开此前跳过的问题，但只修已明确部分。
- 复用已确认设计、验收与授权；完成需求所必需的关联脚本可纳入同次备份、构建、验证和审查，并说明原因，不因多一个文件重复申请同一授权。改变玩法、删除既有进度、扩大部署对象等仍需单独依据。

## 缩短交付等待

- 正常路径用一个新档走通，修后用独立测试槽复验受影响阶段。长会话只带操作决定、异常和证据路径。一个只读采样进程负责短时连拍，按状态变化选关键帧。真实点击、裁字、奖励和异常仍看原图。长历史主会话单次输入已达数十万且要连续操作时，若同一桌面工具确实可用，把必要步骤、当前窗口与权限交给一个不继承旧历史的操作上下文，由它独占窗口，主聊天只接收关键帧和结论。仅主聊天能操作时保留原入口，合并动作与读回。截图、计数、哈希、轮询与归档由脚本或协调者执行，仅在独立判断有收益时增加模型代理。
- 同一目标上的确定输入分成小批，批后读回状态。新弹窗、目标移位或工具失败时停止该批。桌面工具超时先重绑窗口并核对已写入值，接着完成余下动作。遇到较长等待，及时说明所等的结果。
- 原需求、适用规则、源码及证据已齐时，阶段默认加 `--snapshot-only`，直接基于冻结材料产出。该模式省去技能清单、关闭 shell、Apps 和插件。需要角色主动找文件、使用工具或写代码时沿用普通入口。阶段用量从 `receipt.json` 的 `usage` 读取，旧回执可查同目录 `events.jsonl`。
- 对同一候选先批量运行独立检查。已复现的门禁失败或真机差异可直接执行 `revise --from <Sol候选目录> --failed-check <UTF-8回执>`，回执附候选指纹、期望、实测和未关闭事项。证据有歧义时再交 Astra 分析。最终发布须由 Astra 独立验收，保留必要的部署后实机复验。

- 开工用一句话确定本轮变更边界和最小验收集；先完成受影响部分，不把历史全套检查自动加入。当前主题状态、相关源文件与所需技能读一次即可；恢复时核对差异，不从头重读历史。
- 局部画面/参数修订默认直接实现、定向检查和一次必要冒烟；新增关卡优先验证新增数据、特殊机制、入口及相邻切换。只有共享规则、公共渲染/状态机改变、依赖无法界定或定向检查暴露跨域故障时扩大回归。具体复用条件见[验证与审查取证](references/verification.md#按改动选择验证与复用)。
- 独立审查依据实际修改的风险触发。新增关卡、调用已验证的胜败流程或按钮文字变化，本身不等于修改“结算触发”；结算条件、去重、奖励、存档和跨端状态链真正改变时仍执行关键审查。
- 候选冻结后，独立的测试与必要审查可以重叠进行；共享同一模拟器、活编辑器或输出文件的操作必须串行。已有原始证据交审查者复用，不安排多方重复跑同一全套；审查通过仍以所需证据齐全为准。
- 把同一轮局部改动合并后构建；先跑便宜的针对性检查再启动昂贵的端到端回归。失败后只重跑修复所影响的检查；无新增变化、失败或疑点时，通过即进入部署，不追加“保险测试”。
- 优先利用现有测试的关卡/用例筛选、就绪信号与报告能力；确因重复手工操作拖慢时才补小型辅助工具，不为提速先建一套框架。耗时异常时记录最慢阶段及实际用时，下一轮优化该瓶颈，不预先承诺提速百分比。

## 自主分工

此分工适用于已启动工作流的文案与代码任务。Astra 只读分析需求、现状和复杂根因，给出 Sol 可直接执行的大纲与验收条件，再只读验收。Sol 按大纲写成稿或实现代码，负责自检、返修、最终成果及授权内发布。普通问答不启动工作流，简单任务可缩短大纲与验收。

- 简单修改、频繁视觉反馈或拆分收益不足时，由 Sol 直接实施，Astra 简短明确方向和验收条件；应查看参考与成品，最终视觉由用户验收。
- 有清晰独立边界、专门能力需求或可靠并行收益时委派，简短说明目的。同一源码或物料范围只有一个写入者；并行范围必须互不冲突，已有执行者占用时先交接。
- Sol 完成必要自检后，由 Astra 按冻结候选与设计条件只读验收；简单任务保持验收简短。实际修改存档恢复、奖励去重、结算触发、跨端同步等关键行为时，由未参与实现的 Astra 定向审查关键逻辑及受影响调用链；已覆盖部分不再叠加审查。

### 使用独立 Codex 根派发

1. **选择模型与档位。** 每阶段由主聊天通过 [阶段启动器](scripts/run_stage.py) 调用本机官方 `codex exec --ephemeral`，启动一个新的独立根。Astra 家族负责规划、审查与复核，使用 Fast（`priority`），通过 `--effort` 传入当次有效的 Astra 推理强度，默认采用可核实的主聊天当次强度。Sol 家族负责成稿、代码、自检与返修，使用 Fast+（`ultrafast`），推理强度固定为 `medium`。启动器默认按宿主目录选择各家族最新可用的正式主力型号，跳过预览、快照及虚构别名。用户指定精确型号时传 `--model`。可用 `--tier` 显式声明该阶段约定的档位。型号、档位或推理强度无法确认时说明具体缺口。
2. **准备交接。** 使用同一目标工作区及同一主题入口。主聊天核对 UTF-8 任务单，放在临时运行目录体系内。任务单包含原始需求、已确认决定、授权、相关 AGENTS、资料与验收入口。规划成功后主聊天核验大纲，再交给 Sol。之后每轮通过 `--from` 传入前一成功阶段目录，核对传递的原始任务、大纲、冻结候选和适用的上轮审查意见。当前阶段只接续所需工作；Astra 与 Sol 是贯穿任务的两个逻辑角色，每次调用启动各自独立的临时根。阶段启动器固定载入发行随附的 [Astra](assets/agents/astra.toml) 与 [Sol](assets/agents/sol.toml) 角色指令。项目 `.codex/agents/` 仅供比对，差异记录在 `receipt.json`。
3. **授权写入。** 只有 Sol 的 `draft`／`revise` 可在明确获准修改代码时以 `--write-code` 写入目标 `--workspace`。直接交付文字时省略该开关，由主聊天原样转交通过验收的成稿。主聊天在冻结候选通过 Astra 验收后，按既有授权与项目工具协调发布、部署和回执。每个阶段完成后核对产出及 CLI 执行回执，分别记录模型与档位请求、可见的线程及回合完成证据。服务端实际生效或计费档位需要相应回执，CLI 退出码 0 及回合完成事件仅代表阶段已返回。验收以 Astra 对确切候选的实际结论为准。原生子代理继承父会话档位，无法提供这套独立分档；普通项目聊天沿用本身的 Fast 设置。
4. **处理故障。** 保留已完成的阶段、原始回执和恢复点。短暂容量故障可对同模型有限重试，同时完成独立工作。CLI、选定模型或必要审查持续不可用时标明阻塞及未验证项，不静默换模型或用继承父档位的派工替代 Sol Fast+。

以下为 PowerShell 示例，使用 Python 3.11 或更新版本。`$runner` 指向本技能的启动器，`$work` 是授权的目标工作区，`$run` 是该工作区内供本轮使用的临时日志根，`$effort` 是本轮已核实的 Astra 推理强度。每次调用在 `$run` 下创建新的阶段目录，依次将成功返回的实际路径填入 `$planDir`、`$draftDir` 和 `$reviewDir`。成功阶段保留 `output.md`、`receipt.json`、`inputs/` 和 `events.jsonl`。

```powershell
python $runner plan   --workspace $work --run-dir $run --task "$run/task.md" --effort $effort
python $runner draft  --workspace $work --run-dir $run --from $planDir --write-code
python $runner review --workspace $work --run-dir $run --from $draftDir --effort $effort
python $runner revise --workspace $work --run-dir $run --from $reviewDir --write-code
```

审查退回或已有可复现的失败回执时执行 `revise`。返修后用新的目录执行 `review`，其 `--from` 指向成功的返修目录，并交接上轮意见与旧候选。纯文案也使用同一交接顺序。

### Windows 沙盒或项目工具受限时

保留原沙盒权限。本机 Windows 后台阶段出现 `CryptUnprotectData`，或独立根无法访问目标工程所需工具时，主聊天用已有授权工具核对原始源码、契约和哈希。放入规划任务单，或在非 `plan` 阶段通过 `--evidence` 提交 UTF-8 证据文件。启动器保留当次快照和哈希，每阶段按需显式传入。

Sol 在默认只读模式交付完整文件或可机械应用的补丁。主聊天先核对原文件指纹，再按原样应用，执行必要测试并重读实际候选。遇到 BOM 或换行敏感的文件，要求 Sol 返回可验证补丁或无损编码，分别核对补丁、原文件和应用后文件的指纹。保留实际字节格式，避免用 CLI 返回的 Markdown 或源码文字直接覆盖 CRLF 文件。将实际文件内容、哈希和测试结果通过 `--evidence` 交 Astra 复核，注明哪些证据来自主聊天的工具快照。Astra 绑定确切候选，证据不足时保留阻塞。可正常写入的沙盒继续使用已授权的 `--write-code` 路径。两条路径均在验收通过后按原门禁交付。

## 执行与返修

1. **明确范围与大纲。** 主聊天调度 Astra 给出范围、可执行大纲及可观察的验收条件，再连同任务单交 Sol 执行；仅在影响方向、范围、权限或外部依赖时集中确认。普通技术问题自行解决。
2. **Sol 实施。** 按大纲完成文案成稿或代码实现。读取当前真源与基线，代码任务按项目规则备份、从唯一入口构建。缺陷修复先取足以支持改动的证据，关键或有歧义的问题优先用旧版同操作复现；不能复现时记录静态证据与不确定性，不凭猜测扩大改动。给执行者提供工作区路径、相关 AGENTS 入口、同一主题文档、明确范围、写入边界、验收及部署权限；禁止扩改相邻任务或自行再派代理。
3. **Sol 验证与冻结。** 缺陷、关键状态或验证争议按需读[验证与审查取证](references/verification.md)，选受影响路径的必要检查。文件候选返回各候选路径、实算 SHA/bytes、实际差异、适用的备份、证据和未验证项；冻结该范围源码、构建入口和产物，停止相关后台写入。聊天内交付的文案提交确切版本全文。只追加不改变候选的证据可与审查并行，所需证据未齐不能放行。
4. **Astra 只读验收。** 绑定候选版本、范围与实际差异；文件候选绑定指纹。预先分析固定基线不等于最终候选审查。审查者只产出审查证据，不改源码、部署或另建主题交接。每项阻塞给位置、触发、证据、影响和通过条件；关注实际状态与受影响调用链，不只看按钮显隐或成功分支。复用可信的同版本证据，有疑点再定向复现；结束时复核候选，结论只覆盖所审版本。
5. **返修。** 将 Astra 的阻塞意见交 Sol 后解冻，修完重新构建、验证并冻结。新的 Astra 审查阶段接续前轮意见，复核新候选修复点及受影响部分，未变文件/检查可复用，不因轮次变化全量重跑。无证据支持的额外改动应收窄。同一问题两次实质返修仍失败，最迟交 Astra 只读分析根因或调整设计，再由 Sol 修复；已有 Astra 则换取证方法；不把普通调试抛回用户。
6. **外部阻塞。** 只有需要改变产品方向、范围、权限或无法独立解决的外部条件时才集中请用户决定，并保存具体证据与恢复点，不删验收项或虚称通过。

## 发布、部署与验收

- 每轮先由 Sol 完成候选与必要自检，再必经 Astra 验收；风险决定验收深度，不决定是否验收。设计与验收可由同一未参与实现的 Astra 承担。授权已覆盖发布/部署则继续，不重复索要；未覆盖时提供具体可审阅版本再确认。
- Astra 对最终冻结候选验收通过后，主聊天按已获授权安排 Sol 按项目规则完成发布/部署，并在阶段启动器缺少项目工具时协调原工具入口。执行前核对指纹、归属、备份与门禁；发现活文件并发变化先停止并报告，不覆盖。部署中断先核实结果，不盲重试。部署产生必要新事实时，由 Astra 只读核对回执。
- 门禁报错先区分实际缺陷、判据误报与工具不可用。已有失败方法不盲重跑；替代检查或例外须符合工程规则并保留依据，不伪造图源、删检查或把未判定项写成通过。工具参数与替代路径留在工程技能/当前证据中，不固化某次环境故障为通用豁免。
- 分别记录部署后 SHA、编辑器存盘、`.gil` 同步及真机试玩。静态或模拟器证据不替代真机，未做项明确标注；纯物料任务不套用游戏部署流程。

## 状态与交付

- 主聊天统筹同一主题文档内容，调度用的临时任务单与回执随运行目录保留，项目文件、证据与主题文档由 Sol 在已授权的可写阶段更新；只读路径由主聊天按上节应用 Sol 的候选并保存证据；Astra 只返回文字。按工作区 AGENTS 统一回写同一主题文档，顶部保持更新时间、当前状态与下一步；用已完成/未完成事项区分实现、验证、审查、部署、存盘和用户验收，待办写责任方及通过条件。执行者、审查者提交事实和原始证据，不各建一套任务书/交付/交接。共享技能仓库沿用 `handoffs/active/` 的对应主题；只有目标工程明确采用 `work/交接.md` 时才更新其中的本主题摘要和入口。写前核对并发变化，保留其他任务内容。
- 更新对应事项并压缩过期中间状态，不逐轮堆积重复正文。保留有效决定、最新核实指纹、未完成依赖和必要证据入口；原始回执、审查证据与回滚备份可独立存放，不因精简主题文档而删除。
- 调度只在当前聊天活跃期间运行，不承诺关闭后继续。已授权工作持续到实现、必要验证、返修及授权内的部署完成，不停在首版、候选或“已派工”；工具或额度中断时说明恢复点。恢复先核对阶段回执和当前文件，不重复派工；技能更新不主动中断或重派在途任务。
- 进度沟通优先说明新发现、决定和剩余风险，不为凑更新重复计数或内部过程。最终简报结果、必要验证和未完成项，按工程规则给出指纹、备份及证据入口；必要复查通过即停止。区分规则已写入、制作/实现完成、自检或审查通过、已部署与用户验收；配置或规则校验不等于流程实跑通过。
